# Open Agent Memory Operations

## Overview

OAM uses one canonical behavior file and explicit operator commands. No required role silently falls back to a provider or model; no accepted asynchronous write depends on a client connection remaining open.

Source passage sizing and final embedding admission share `models.embedding.tokenizer`, which defaults to `auto`. Exact recognized model names select the OpenAI `cl100k_base` counter or the bundled official Qwen3-Embedding tokenizer. Unknown names use approximate `o200k_base`. The scalar `openai` preset selects `cl100k_base` and an automatic per-input limit of 8192; `qwen` selects the corresponding recognized Qwen3-Embedding asset, otherwise the approximate 0.6B asset, and an automatic per-input limit of 32768. For online Qwen models without a published size label, set `tokenizer: qwen` to use this approximate Qwen3 preset. An explicit numeric `max_input_tokens` always overrides the preset, and explicit null remains unbounded. Request-total and item limits remain model-derived or explicitly overridden. A tokenizer object selects a configured local counter; explicit `null` retains the general `tokenizer.type`. Extraction estimates, Profile accounting and live recall retain their separate existing policies.

The embedding binding's `max_input_tokens`, `max_request_tokens` and `max_request_items` independently default to `auto`. Each accepts a strict positive integer override or legacy `null` for no local bound. The resolver uses the literal configured model or its `model_env` value from the supplied process environment, without endpoint or credential inference. Runtime snapshots the environment at construction; restart processes after model changes. An absent embedding binding retains the general counter and unbounded legacy behavior. A counter choice alone does not prove serving-tokenizer parity; all current local embedding counts remain marked estimated.

| Exact model profile (case-insensitive) | Counter | Per-input tokens | Request-total tokens | Request items |
|---|---|---|---|---|
| `text-embedding-ada-002`, `text-embedding-3-small`, `text-embedding-3-large` | `cl100k_base` | 8192 | 300000 | 2048 |
| `Qwen/Qwen3-Embedding-0.6B`, `-4B`, `-8B`; bare `Qwen3-Embedding-<size>`; local `qwen3-embedding:<size>` | Corresponding bundled tokenizer, with EOS | 32768 | Unknown | Unknown |
| `kinfra-text-embedding-0.6b`, `kinfra-text-embedding-4b` | Approximate `o200k_base` | 32768 | Unknown | 128 |
| Other identities | Approximate `o200k_base` | 8192 | Unknown | Unknown |

The table lists model-derived defaults used by `tokenizer: auto`, tokenizer objects and legacy null. Scalar `openai` and `qwen` presets override only the automatic per-input limit as described above; they do not override request-total or item limits. Only these exact model names are recognized; other namespaces, suffixes, generation, reranker and multimodal names are unknown. Unknown request limits mean no additional local bound, rather than unlimited provider capacity. OpenAI's profile follows its [embedding API limits](https://developers.openai.com/api/reference/resources/embeddings/methods/create). The bundled Qwen files load offline, verify their pinned hashes and preserve exact content-based counter identity; [third-party notices](../THIRD_PARTY.md) record provenance. Operator aliases assert a local model identity and cannot establish remote serving parity.

Before HTTP, runtime and preflight trim each oversized embedding payload to an original Unicode prefix within `max_input_tokens`, counting the complete final input including query prefixes and tokenizer special tokens. A warning records the item index, original and retained token counts, limit and tokenizer identity without source text. Stored sources, facts and original queries remain unchanged; only the embedding represents the retained prefix. If no nonempty prefix fits, preparation fails before HTTP. Explicit `max_input_tokens: null` disables this trimming. Request-total and item limits apply after preparation and still reject the whole batch; OAM never trims to fit a request-total limit, repacks a batch or dispatches only part of it. Source chunk sizing continues to preserve complete source coverage while observing the effective per-input bound.

Hosted `text-embedding-v4` is outside the raw Qwen profile and uses the unknown fallback. Its [hosted API](https://www.alibabacloud.com/help/en/model-studio/embedding-interfaces-compatible-with-openai) documents 8192 tokens and 10 items; that hosted profile is unsupported here and requires compatible explicit configuration and caller batch sizes. OAM does not repack requests. Tencent's [model list](https://cloud.tencent.com/document/product/1823/130051#vec-model-list-section) lists 32K context for the recognized KinFRA text models; OAM applies a 32768-token input limit. Its [embedding API](https://cloud.tencent.com/document/product/1823/133515) recommends at most 128 texts. OAM uses 128 as a default product cap, not a claimed server hard limit. KinFRA 4B returns fixed 2560-dimensional vectors, exceeding OAM's current 2000-dimension ceiling, so its recognized token policy does not imply end-to-end support.

Live recall uses cached local `o200k_base` counting for complete tentative and returned context strings, independently of the embedding binding. Its counts include citations, quotes, aliases, dates, formatting and separators. Existing rendering bytes and compact/full formatting choices remain compatible with recorded replay. Legacy traces are recounted with their recorded Unicode estimator, native traces with `o200k_base`; historical contexts and counts are not rewritten. Exact counts under this vocabulary do not establish the answer model's token usage.

For a local tokenizer asset, configure `{type: tokenizer_json, file_env: OAM_EMBEDDING_TOKENIZER_FILE, add_special_tokens: false}` under `models.embedding.tokenizer`, then set that environment variable to the local `tokenizer.json`. Choose the special-token policy to match the verified serving deployment. OAM loads only the supplied file, disables saved truncation/padding, and hashes its bytes plus special-token policy; it never downloads assets or silently changes vocabulary. Missing or invalid assets fail runtime/preflight. Existing published evidence and user namespaces remain eligible. Resume retains published passage boundaries and reuses checkpoints when their inputs match; an over-limit saved input can still fail explicitly at embedding admission.

Apply all migrations before starting upgraded workers. Interaction indexing publishes extracted facts and temporal links, then atomically saves a source/version/generation-qualified semantic seed manifest, succeeds the direct work unit and queues a dependent `index_semantic_links` work unit under the same source operation. Direct memory is already searchable with `memory_ready=true` and `temporal_links_ready=true`, while `links_ready=false` and the source operation remains `processing`. A semantic worker reads bounded proposals outside the shared user-row lock and publishes guarded batches after rechecking source eligibility, generation, lease and fence. Successful completion sets `links_ready=true`, succeeds the source operation and, when Insights are enabled, schedules separate consolidation with its configured delay. Empty seed sets still pass through the semantic claim and complete without neighbor reads. `worker.claim_semantic_links` can hold queued semantic work without consuming claims. Existing saved inline semantic phases and queued semantic units remain resumable; compatible completed facts, embeddings and checkpoints are reused. A semantic failure does not erase published direct memory; inspect the operation's readiness and failure details rather than treating direct-memory readiness as full link readiness. Wait for `links_ready=true` when complete graph coverage is required.

During content indexing, a completed, unrefused model response with empty, whitespace-only or null content is eligible for the remaining `retry.max_attempts` work budget, which defaults to three total attempts including the first. Successful checkpoints are reused and failed-response usage remains recorded; exhaustion reports failure rather than a successful `no_facts`. An explicit `{"outcome":"no_facts","facts":[]}` remains a successful result without retry. Refusals, reasoning-only responses, tool calls and other malformed responses retain their existing failure behavior. This adds no model-client retry loop and does not change semantic-link retry policy.

Release runtimes need the system PostgreSQL client library (`libpq`) before installing OAM. The local development dependency group installs the self-contained Psycopg binary extension; release installations omit that group. The release image must retain the system library's license notice.

Fast configures `lexical_ranking: whole_query`, `partial_match_gate: user_fact_exchange` and `adjacent_user_context: true` in [canonical configuration](../configs/oam.yaml). Normal sets them to `per_term`, `"off"` and false. The source-seed limit additionally bounds the raw dense prefix used for fact-and-original corroboration of partial assistant replies; it does not restrict optional user context to the first packed facts. These use existing dense, lexical and source-provenance data; fast always skips a model reranker. With the gate active, supplemental user-original discovery uses independent user-fact source revisions and the existing global source-seed cap; these originals compete after their fact owner without authorizing assistant replies or further recovery. Inspect `diagnostics.local_context`, `local_context_selection` timings and the correlated recall log to confirm the configured gate ran. `recovery_sources`, `recovered_user_originals`, `selected_recovered_user_originals` and `source_user_context` distinguish eligible sources, discovered complete originals, final complete originals and their fact owners; an excerpt is excluded from the complete-original count. Partial recall with unavailable dense retrieval reports `dense_unavailable` and retains lexical results. Optional adjacent user context uses the per-mode `adjacent_user_context_max_chars` character cap from canonical configuration: the previous user passage's tail and next user passage's head. Sentence punctuation takes priority over clause punctuation, with numeric/abbreviation safeguards; optional text without a fitting proven boundary is omitted. Required cited bodies remain complete. Excerpts carry character-range metadata and visible context markers, share existing item/token caps, and are skipped when chunks are disabled or the excerpt cannot fit. Diagnostics and correlated recall logs report the effective cap. Restart API processes after changing recall configuration. Changing these retrieval fields does not rebuild or rewrite indexed content.

Each recall mode configures graph and causal_graph independently. Graph selects off/light/full for entity/alias and semantic expansion; causal_graph toggles outgoing causal links in both ordinary and temporal retrieval. Fast defaults to off/false and normal to light/false. For a complete graph shutdown use both graph: "off" and causal_graph: false; temporal date filtering and temporal links continue. The legacy fast_graph request override affects only entity/semantic selection. Inspect diagnostics.graph, diagnostics.causal_graph and correlated recall logs when comparing configurations.

## 1. Configuration

### Optional decision model

`models.decision.enabled` and a nonblank model identifier in its `model_env` must both be present to activate the general decision client. The canonical binding uses `DECISION_MODEL`, `DECISION_BASE_URL` and `DECISION_API_KEY`, independently of the VLM settings. Set `enabled: false` to disable it even when those variables exist. A missing or blank model identifier also disables it without endpoint/key lookup; an active binding requires a valid HTTP(S) endpoint and nonblank credential. Model names pass through unchanged; provider availability is established by a real preflight, not a name whitelist.

The supported protocol is Jev-compatible `system_one`: OAM sends Bearer-authenticated `POST {base_url}/systemone` with `model`, text `state` and named `questions`. A base URL already ending in `/systemone` is used directly. Choice questions use a nonempty map of labels to descriptions; `noul` returns a yes/no probability; score questions use an ordered list of at least two levels and return a fractional index from zero to the last level. `oam.models.decision.DecisionQuestion` defines these inputs; `RuntimeModels.decide(state, questions, timeout_seconds=...)` returns typed answers, reported model provenance and usage. Choice/confidence probabilities must be finite and in range; a supplied distribution does not replace the provider's chosen label. Missing usage stays unknown.

`oam preflight` tests known choice, positive/negative probability and score judgments when the binding is active; a failed decision probe makes preflight fail. Startup/readiness validate active configuration without inference. Runtime calls reuse existing model deadlines and LLM capacity admission, make one transport attempt and report invalid/missing/refused answers as errors. Callers own semantic uncertainty, fallback and spending admission; direct decision calls are not automatically charged to the source-generation budget. Restart API and worker processes after changing these settings. This client does not activate an L2 shortcut, Profile update gate, automatic refresh or retrieval reranker; those policies require separate consumer integration and acceptance evidence.

### Vector-index policy

`database.vector_index_mode` selects `small` (the default shared HNSW), `large` (one partial HNSW per tenant/user), or `growing` (shared until `database.vector_index_min_rows`, initially 10,000 embedded search units). These are physical policies, independent of recall level. Changing policy preserves facts, vectors, content-generation identity and completed model checkpoints. Vector discovery uses ANN; exact scoring may still rank an already bounded set of graph/support candidates. Shared graphs can return fewer matches under selective owner filters, so evaluate candidate coverage and latency on the intended user distribution.

Run `oam vector-indexes --config <operator.yaml> --once --tenant-id <tenant> --user-id <user>` to provision or verify one owner's index. Omitting `--user-id` selects that tenant, and omitting both selects the database's active users. The command uses the configured migration DSN and requires unfiltered operator authority; content roles remain unable to create indexes. Concurrent maintenance is serialized by a database session lock, so use a direct or session-pooled operator connection. Catalog checks validate the exact table, owner predicate, cosine operator class and ready/valid state; a name collision fails safely, and an interrupted invalid build is repaired without re-extraction.

For automatic provisioning, supervise `oam vector-indexes --config <operator.yaml>` as a separate privileged maintenance process. It reconciles every `database.vector_index_poll_seconds` (900 by default), builds with `CREATE INDEX CONCURRENTLY`, and retains valid dedicated indexes when collections shrink. Counts stop at the required threshold and never run on recall. SIGINT/SIGTERM stops the next owner build and drains the current one; a 15-minute statement timeout bounds maintenance SQL. Verify actual shared or owner-index execution after provisioning; catalog presence alone does not prove query-plan selection. Automatic switching and operator failures never release content-work holds or reset model attempts.

### Insight scheduling

`index.insights_enabled` enables automatic L2 Insight synthesis. `index.insight_consolidation_delay_hours: 24` makes each new consolidation job due 24 hours after the complete source pipeline finishes, including semantic links; configure a positive number of hours, such as `0.5` for 30 minutes. Replace `insight_consolidation_delay_seconds` in older operator overrides with this hours key and divide its value by 3,600. This is a per-source delay, with no periodic global sweep. Restart API and worker processes after changing it. Existing queued jobs keep their stored due times, and changing only this delay does not invalidate indexed content.

The per-user consolidation claim hold is disabled by default and intended only for controlled evaluations. Ordinary L2 indexing proceeds without an operator action. When explicitly enabled, the hold keeps queued L2 work from starting across worker restarts. It does not stop already running work, alter due times or consume attempts; establish it before work starts or drain existing work first. Releasing the hold makes already-due work eligible for ordinary workers. The hold is database state rather than an indexing or recall configuration setting.

Use `oam l2-hold --config <operator.yaml> hold --tenant-id <tenant> --user-id <user>` to hold, and replace `hold` with `status` or `release` to inspect or release it. The command uses only the migration DSN selected by the operator configuration and requires its effective PostgreSQL role to have `BYPASSRLS` or superuser authority, so running work cannot be hidden by row-level security. Application credentials do not grant this authority. Status reports the durable hold and the count of running consolidation work. Holding is rejected while any consolidation is running, including an expired claim that still needs recovery. The command does not cancel work or make future-due jobs immediately due.

After enabling Insights over completed L1, run `oam l2-index --config <operator.yaml> --tenant-id <tenant> --user-id <user> --limit <source-count>`. This operator-only command queues at most the requested number of active, current interaction sources with eligible completed L1, using their original generation and existing consolidation identities. It makes no model calls or L1 changes. New jobs are due immediately, respect the user's hold and ordinary worker limits, and report `scheduled`, `scheduled_count` and `queue_full`. Existing consolidation jobs are skipped, including failed jobs: use their existing retry path instead of creating replacement work. Repeat the command to admit further sources after workers drain the queue.

Set `index.generation_token_budget` to a positive integer before a bounded interaction-indexing run; null disables admission budgeting for new sources. The workload unit is one interaction source/version/generation, covering L1 and L2 text generation, failed calls and retries; Profile, embeddings and document Resources are separate. The original source operation pins the limit. Every actual generation call, including an extraction split retry, reserves the serialized text-request UTF-8 byte count plus its full output-token ceiling before HTTP, under the existing user lock. This conservative text-token allowance is not a provider-reported usage measurement. Reservations are never refunded; failures and unknown outcomes remain charged, and a pinned limit remains effective after configuration changes. Existing complete generation usage seeds the counter when enabling a budget over prior L1; ambiguous history blocks new dispatch. Chat and Messages have supported output ceilings; bounded mode rejects Responses generation because its current wire path omits that ceiling. Inspect `index_generation_budget` logs and the source operation's `index_generation_budget` state, and report reserved allowance separately from actual generation usage. Budget refusal leaves unfinished work and completed L1/checkpoints intact; it does not shorten an output budget to force a call through.

`chunk.ingestion` splits each message or document into passages with a 2,048 estimated-token target, 4,096 maximum, zero owned overlap and 128 prior context-only tokens. These passage limits apply to singleton and grouped extraction. Blank lines define paragraphs; a single wrapped newline does not force a split. Pack whole paragraphs when they fit, otherwise subdivide by multilingual sentence punctuation, then clauses, whitespace and finally bounded characters. Greedy packing may cross the soft target to finish a unit, but never the hard maximum. The chunker owns every input character in contiguous nonoverlapping spans; whitespace-only pieces are excluded from model inputs while the accepted original remains unchanged. Overflow retries use the same punctuation detector near the midpoint and preserve both exact source substrings. Existing eligible records remain readable when chunking settings change. Interaction, plain-text Resource and native PDF retries retain published passage boundaries and process the remaining source text. Resource retries reject a conflicting published parse. Recall uses one complete-rendering cap per mode: `search.fast.context_max_tokens: 18000` and `search.normal.context_max_tokens: 32768`. Chunks are included by default; strict boolean `include.chunks: false` excludes all full source bodies while retaining eligible learned items, required supporting facts and citations. Source eligibility and complete support are checked in either case. Shared chunks are counted once; complete bundles that do not fit are omitted without clipping. The only eligible L1 fact may return its complete oversized bundle alone if no higher-ranked root was admitted; filling stops and diagnostics report the overshoot. Insights have no such exception. `search.<mode>.max_results` bounds learned items and full originals separately. Recall-only settings do not affect indexing. Remove legacy `context` configuration and `chunk.recall` settings; there is no configured tokenizer selector or independent text-budget default. Capabilities publish each mode's context cap. The runtime estimator identifies its counting implementation in recall responses; exact model-input counts belong to callers. Profile previews retain their separate `profile.max_response_tokens: 18000` default and ceiling. `profile.max_memory_tokens: 32768` bounds the serialized selected memory evidence and provenance independently of the system prompt, exact fields and instruction. `profile.max_input_tokens: 49152` separately bounds the complete system prompt and serialized request using the configured tokenizer. The stricter applicable limit determines whether a candidate fits; the worker logs both token counts and limits. The tokenizer count is not necessarily the provider model’s count or a guarantee that its context will fit; operators must choose a suitable tokenizer and budget and leave room for output and reasoning.

Message grouping is enabled by `extraction.group_max_passages: 64`. A short eligible source uses one extraction call when its complete serialized input and estimated output fit the configured bounds; longer sources split into source-ordered groups without crossing an ineligible message. Set the value to 1 for singleton extraction. `extraction.group_max_estimated_output_tokens: 4096` bounds the group planner estimate, while `extraction.max_output_tokens: 64000` supplies the Chat completion budget for extraction; the Insight budget is configured separately. Messages requires a completion budget, while Responses omits it and relies on the request deadline. Raising a completion budget does not enlarge groups because planning uses its separate budget. Length-truncated responses trigger recursive split-and-retry at passage boundaries, then within a singleton source span near a sentence boundary. Truncated content is never published. Unsplittable overflow remains a failure; malformed JSON and other provider failures do not trigger splitting. Each child rechecks cancellation and source eligibility and renews its fenced lease before dispatch. Resource vision and abstract requests use `resource.max_output_tokens: 4096` as their Chat/Messages completion budget; Responses omits a request output limit. Child calls run in source order under the existing outer checkpoint, and their usage is aggregated with overflow attempts; incomplete split trees are retried as a whole. Changing these extraction settings changes the recipe for new work; existing completed projections remain readable. The default reduces calls for short sources, while real-model coverage, generation tokens and phase 1 latency still require evaluation.

The extraction prompt selects significant reusable claims and preserves consequential one-time events, entities, state-update links, qualifiers and date evidence. It excludes boilerplate, generic advice and acknowledgment-only promises. Source support uses stable passage/source/message identity and one unchanged unique quote. In grouped extraction, a missing or invalid passage identifier is recovered only when its unchanged, nonblank quote occurs exactly once across all offered passage bodies. Context-only text and existing-fact references cannot establish ownership; ambiguous matches and quotes that contradict a valid supplied owner remain rejected. Recovery retains the output index and records a `recovered_passage` diagnostic, so the source remains marked partial and ordinary fact/metadata validation still applies. Character coordinates are absent from extraction envelopes, caller/generated temporal annotations and stored passage/fact locators; ambiguous quotes require longer exact context. Temporal annotations share role, timezone-aware start/end and exact quote. Point/period range inclusion and origin come from the server; source/request metadata owns reference timezone. Precision, uncertainty and duration stay in fact text and quote. The current indexing recipe is `oam-source-fact-insight-v37`. Existing completed projections remain readable; startup neither rewrites nor deletes stored data. Before upgrading an existing deployment, drain accepted pending work using its original contract. Original annotated envelopes containing retired character or temporal classification/provenance fields cannot be replayed by the new strict contract; the generation recipe does not rewrite accepted originals. Existing stored data is not migrated or deleted automatically. Prompt examples and deterministic tests do not establish full-history quality or indexing-latency parity.

`index.enable_causal_graph` defaults to `false`: extraction uses the shared entity/time/update prompt without structured causal links. Setting it to `true` appends causal instructions and the link field for the shared example, and stores validated effect-to-cause links. Disabled extraction discards unsolicited `caused_by` values without dropping otherwise valid facts. This indexing choice changes generation. Independently, `search.fast.causal_graph` and `search.normal.causal_graph` default to `false` and choose whether each recall mode reads existing causal links, including temporal spreading. These query choices require no reindexing and can run causal-only expansion with `graph: "off"`; the indexing flag does not override them.

Existing-fact extraction context is enabled by default alongside message grouping: `extraction.reference_max_facts: 10` allows up to ten facts, and `reference_max_input_tokens: 2048` is a configurable soft estimated-token target. The worker freezes complete eligible candidates and derives one proportional text preview for the extraction request. All text lengths use the same ratio after serialized metadata is accounted for; no short-first reservation or quota redistribution applies. Previews end at a nearby sentence or comma boundary, so the reference total may exceed the target. Shortened previews carry `text_truncated: true`, preserve IDs, speaker roles and time metadata, and remain incomplete context whose missing qualifiers are unknown. Stored facts and the complete new source are unchanged. `max_input_tokens` still hard-bounds the entire serialized model input; reference admission retains a prefix of relevance order without skipping a large higher-ranked record to fill with lower-ranked ones. Set the fact limit to 0 to disable reference context. Selection reuses passage embeddings and adds no generation call. Changing reference settings or the indexing recipe does not require rebuilding completed collections. Quality gains and phase 1 time require matched real evaluation. Report embedding tokens separately.

`configs/oam.yaml` owns authentication mode, limits, role aliases, retrieval/profile policy, worker concurrency, leases, and retention. An alternate operator YAML may override selected fields; omitted fields come from the canonical YAML, never a second set of Python numeric defaults. At CLI startup, inherited process variables take precedence and `./.env` fills only missing variables. Environment variables supply the PostgreSQL DSNs, the private `OAM_ROOT_API_KEY` value when operator-supplied, model identifiers selected through `model_env`, model endpoint/key values referenced by the selected binding, operator secret-handoff destinations, and an optional alternate config path. An environment variable never overrides a behavioral default invisibly.

API and worker commands reject missing or malformed required PostgreSQL connection strings and unresolved enabled model bindings before starting their services. Migration validates only its migration connection configuration; it does not require model credentials. Startup validation performs no model calls. Use `oam preflight` separately to verify actual provider capabilities.

Required roles are extraction, Insights, embedding, Resource abstract and Profile generation. Generative roles share `models.vlm`; embeddings and optional reranking have separate bindings. VLM `protocol` is `openai_chat`, `openai_responses` or `anthropic_messages`: Chat appends `/chat/completions` to its configured base, Responses appends `/responses`, and Messages appends `/v1/messages`. Use the endpoint base for the chosen protocol; Messages uses `x-api-key` and `anthropic-version`, while the OpenAI protocols use Bearer authentication. `models.reasoning_effort` keeps `null` as role disabled; other values enable the role. `reasoning_mode: legacy_chat` preserves the existing Chat thinking and effort fields. `effort` sends the protocol-specific effort field; `provider_default` explicitly omits reasoning controls. New non-Chat bindings require an explicit non-legacy mode. `reasoning_split` is Chat-only: `null` omits it, while `false` and `true` are sent unchanged. Provider support for these options, structured output and vision varies; run preflight against the actual endpoint. Extraction preflight requires both text and vision. Complete leading reasoning blocks in Chat responses are separated before JSON validation; incomplete or reasoning-only output fails. For Messages responses, reported cached and uncached input tokens are included in usage totals. Model usage and logs expose cached, uncached and cache-creation input counts when reported; unknown breakdowns are null, and input totals remain inclusive. OAM does not store prices or calculate cost.

`models.embedding` separately declares its model, endpoint, optional key and `embeddings` capability with `protocol: openai_compatible`. `index.embedding_dimensions: 1024` owns the vector size used by database initialization and runtime validation; the endpoint must return that size. An unauthenticated embedding endpoint can set `models.embedding.api_key_env: null` in its operator YAML. `models.reranker` is a separate optional scoring-model definition with the `rerank` capability; it is null by default. Enable the optional planner by selecting its effort under `models.reasoning_effort.planner`; it uses the same VLM. Preflight verifies actual role-specific behavior rather than trusting model names or configuration presence.

Operator YAML using the former `models.roles` and `models.bindings` alias map is rejected. Move the shared generative definition to `models.vlm`, move its role efforts to `models.reasoning_effort`, and move embedding/reranker definitions to their named fields. Remove per-binding `thinking` and `reasoning_effort`. The database requires the configured embedding dimension to match its vector schema. Equal dimensions do not guarantee compatibility between embedding models; operators changing models must plan re-embedding when needed. Model and recipe changes do not automatically rebuild completed collections.

## 2. Commands

- `oam preflight` resolves configuration, redacts secrets, and tests enabled role capabilities.
- `oam migrate` applies versioned PostgreSQL migrations with a separate migration credential.
- `oam api` runs the FastAPI role, bundled Inspector and, by default, an embedded background runner. Embedded mode requires the queue and worker-content DSNs in addition to the API DSN. Set `worker.embedded_enabled: false` for API-only processes.
- `oam worker` runs the same background processors with separate queue/content database roles. `--once` processes at most one queued work unit and exits. Each runner has up to `worker.max_tasks` concurrent tasks; per-user claims, generation, embedding and indexing DB transactions have independent limits. The embedded flag does not disable an explicitly launched worker.
- `oam model-permits --config <operator.yaml> list` inspects unresolved model-call metadata using the migration DSN's operator authority. API and worker credentials cannot directly update permit records.
- `oam model-permits --config <operator.yaml> reconcile <permit-id> --reason <text> --known-completed` releases a permit after independently confirming remote completion. `--force-unknown` instead acknowledges unresolved remote work and leaves physical concurrency explicitly unverified.
- `oam model-permits --config <operator.yaml> configure` applies changed YAML capacity values after APIs and workers have been stopped. Active HTTP ownership and live/uncertain model permits block the change.
- `oam recover-bootstrap` uses separate administrative database authority to replace a committed bootstrap key whose one-time handoff failed.
- `oam validate-export <directory>` checks a downloaded format-1 manifest, every declared JSONL part and original, counts, hashes and source/support identities without a database or model.

`GET /health/live` reports process liveness. `GET /health/ready` returns `200` only when a bounded read through the API database connection confirms all required migration versions, enabled model configuration resolves, the embedded worker is healthy and its queue/content database connections respond when configured, and model admission is available. Otherwise it returns `503` with a reason and database/schema status. Readiness makes no model calls and does not prove provider reachability. Apply migration `0025_readiness_metadata.sql` to grant runtime roles read-only access to the migration registry before deploying this readiness check.

## 3. Bootstrap and Credentials

The operator initialization step is `oam migrate`, before starting API or worker replicas. Before applying migrations 0017–0021, drain and stop older API and worker processes, run `oam migrate`, then start the new version. Older workers cannot process dependency-bearing Profile jobs from 0018 or write the plural Insight subtypes required by 0020; the new API requires publication time from 0019 and Profile document columns from 0021. With `auth.mode` omitted and neither `OAM_ROOT_API_KEY` nor `OAM_BOOTSTRAP_OUTPUT` set, a fresh database gets the active `default` tenant without a root credential; `oam api` selects `dev` and must bind to loopback. Explicit rootless `trusted` mode also creates that default tenant and accepts local gateway identity headers; nonlocal trusted startup requires an active root key. `OAM_ROOT_API_KEY` stores an operator-supplied root secret as a database digest without writing a handoff file. Alternatively, `OAM_BOOTSTRAP_OUTPUT` names a new operator-only file for a generated root secret; the identity commits before the secret is written once with restrictive permissions, never ordinary logs. Exactly one bootstrap process wins, and interrupted generated-secret handoff requires explicit recovery. An empty root-secret value or simultaneous supplied secret and handoff destination fails. Existing keyed databases keep `api_key` mode when mode is omitted and never silently downgrade to `dev`; incomplete bootstrap fails startup. Application replicas receive only their separate runtime-role DSNs. The administrator creates a user through `POST /v1/users`, receives its first user key once, and uses that key for personal data calls; the root credential itself cannot use personal routes in `api_key` mode.

Positive credential verification may be cached for a fixed non-sliding 30 seconds under the full supplied-secret digest. Invalid keys are not cached. Revocation commits first, prevents an older lookup from repopulating the cache, and reports the maximum cross-process propagation deadline.

After an interrupted `committed` handoff, rerun `oam migrate` to record `recovery_required`, then explicitly run `oam recover-bootstrap` with a new recovery destination. Recovery commits revocation of the lost key and issuance of its replacement before handoff. A further interruption again requires explicit recovery; it never silently creates another administrator.

## 4. Limits and Failure Ownership

The Profile model call has its own 180-second timeout in `profile.attempt_timeout_seconds`; the worker extends only that Profile claim lease for the call, while refresh returns a durable receipt before generation. Each Resource accepts at most 100 MiB of original bytes and 100 PDF pages or 20 image originals; the public image route currently accepts one image. `resource.max_input_pixels_per_image` rejects original images above 100 megapixels before full decoding. `resource.max_pixels_per_image` downscales vision copies and PDF renders to at most 40 megapixels each, preserving originals. `resource.max_total_pixels` imposes a hard 250-megapixel total for original images or rendered PDF pages; this accommodates 100 Legal-size pages at the normal render scale but does not promise every possible 100-page document fits. Report/chat collection-count settings remain reserved and unenforced; the deployment admits 10 simultaneous API requests. An HTTPS Evidence URL has the same 100 MiB content cap and a 30-second total fetch deadline owned by `resource.url_fetch_timeout_seconds`; DNS, connection and body transfer share that deadline. Local PDF parsing/rendering has a separate 30-second child deadline owned by `resource.pdf_child_timeout_seconds`, plus a bounded result transfer. Hard limits remain enforced before model dispatch.

The canonical capacity defaults are:

| Setting | Default | Scope |
|---|---:|---|
| `api.max_concurrent_requests` | 10 | Shared admitted business HTTP requests across replicas |
| `api.max_concurrent_writes` | 6 | Shared mutating requests; four total slots remain available to reads |
| `worker.max_tasks` | 10 | Tasks per runner |
| `database.indexing_concurrency` | 4 | Shared indexing transactions across replicas; model I/O holds no DB slot |
| `user.concurrency` | 2 | Live claims per tenant/user across all runners |
| `queue.max_pending_per_user` | 1,000 | Unfinished root intake requests, including delayed required children |
| `provider.llm_concurrency` | 32 | Shared text/vision generation calls |
| `provider.embedding_concurrency` | 8 | Shared embedding calls |
| `provider.embedding_search_reserved` | 0 | Optional embedding capacity withheld from background work; search may use any free slot |
| `provider.rerank_concurrency` | 4 | Local reranking calls per foreground model client |

HTTP admission covers `/v1/` routes; liveness/readiness and static assets remain accessible without consuming those business slots. POST search is a read for admission. Overload returns retryable `429` with `Retry-After` before body consumption or source acceptance. Each admitted HTTP request holds a separate PostgreSQL session for its admission slot; include up to ten such sessions deployment-wide and short model-admission transactions in database connection planning, in addition to content pools. Runtime DSNs must connect directly or through session pooling; transaction pooling cannot preserve session advisory-lock ownership.

The first API or worker startup freezes shared capacity settings in PostgreSQL. Replicas with conflicting shared limits fail startup. Operator YAML uses independent generation, embedding, worker-task and indexing-transaction limits; obsolete `worker.max_model_calls`, `database.worker_pool_max` and `provider.global_concurrency` keys must be removed. To upgrade an existing deployment to migration 0024 or change shared limits: stop API and worker processes, resolve uncertain permits, run `oam migrate`, run `oam model-permits --config <operator.yaml> configure`, then restart every replica with matching settings. The configurator rejects active model permits, HTTP admissions and indexing transaction slots. Numerical defaults are initial capacity settings; they are not a throughput or latency guarantee.

Intake admission checks idempotency before the root count. Running work, automatic retries and delayed consolidation keep their root slot; an explicit retry needs a new slot. Exact receipt reuse and unchanged Profile refresh still work at the intake cap. Source-deletion cleanup is exempt so that a full intake queue does not prevent source removal. The URL path performs a cheap queue precheck before fetching and repeats the authoritative check when accepting bytes.

Background model requests default to a 600-second timeout in `model.attempt_timeout_seconds`, including capacity wait. Indexing extends its fenced lease to cover that timeout plus the configured renewal margin. Caught transport errors (including read/write timeouts and dropped connections), HTTP 429 and server errors retry unfinished work within `retry.max_attempts`, three total work attempts by default. There is no additional model-client retry loop. Compatible completed checkpoints are reused, and unknown failed-call usage remains partial rather than zero. A caught transport failure releases local model capacity; the provider may still finish and charge for that request, so the limit covers local in-flight calls rather than opaque remote compute.

Model permits distinguish an unused reservation from committed dispatch intent. Unused reservations may expire; interrupted calls without local settlement, including process loss, retain unresolved permits. Each model permit ID is sent as `X-Request-ID` to the provider for correlation. Inspect these unresolved permits with the operator command and confirm remote completion before release, or explicitly force release while acknowledging uncertainty. A fully uncertain pool is visible as blocked in readiness. An explicit forced release preserves the uncertainty record and cannot prove a physical remote-concurrency ceiling.

The worker preserves compatible checkpoints and usage before dependent work. Shutdown stops claims and new model dispatches, waits up to `lease.shutdown_seconds`, and reports incomplete drain when synchronous work survives. Clients remain owned by those tasks until their final completion; a timed wait does not forcibly terminate a Python thread. Work leases, fences and unknown-outcome accounting remain authoritative for recovery.

The API commits Resource revision or all-version source exclusion before returning an operation receipt. Deletion cancels outstanding indexing claims and queues a separate `cleanup_source` work unit; the worker removes affected active-store derivatives, original bytes and held export parts, then marks the cleanup operation succeeded. A failed cleanup stays visible as pending or partial failure and never restores eligibility. New recall, inspection, trace and export reads recheck current policy; an in-flight read that crosses a source change returns a named unavailable or redacted outcome. Backup expiry and restoration proof belong to the later release operations gate, so cleanup success describes the active PostgreSQL store only.

## 5. Current Implementation Status

The implemented core includes eligible interaction and document indexing, supported L1/L2 publication, fast/normal cited recall, explicit stored User Profiles, typed memory/source lifecycle, recorded diagnostics, portable export and Memory Inspector. User listing and stable Insight titles are included in v0.0.2; apply migrations 0036 and 0037 before starting upgraded APIs/workers. Historical completed LME-500 and BEAM-10M results are documented in [benchmarks](benchmarks.md); they are not fresh measurements of the current release. The [v0.0.2 release record](releases/0.0.2.md) states its current verification, while [v0.0.1 candidate evidence](release-evidence.md) preserves the earlier local/provider checks.

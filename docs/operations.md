# Open Agent Memory Operations

## Overview

OAM uses one canonical behavior file and explicit operator commands. No required role silently falls back to a provider or model; no accepted asynchronous write depends on a client connection remaining open.

Apply all migrations before starting upgraded workers. Interaction indexing has two work units under one operation: direct facts and temporal links become readable first, and semantic links finish afterward. During that interval the HTTP operation reports `processing` with `memory_ready=true`, `temporal_links_ready=true`, `links_ready=false` and `stage_state.semantic_links_status="pending"` or `"running"`. The worker renews its lease between bounded semantic batches and computes proposals outside the shared user-row lock. Terminal semantic failure reports partial failure while preserving direct memory; an exhausted expired semantic claim settles on the next queue poll. Automatic database retries reuse the same work unit. The separate public retry endpoint still requires replanning for terminal dependency-bearing work; it does not restart this dependent stage. Wait for `links_ready=true` when complete graph coverage is required.

Release runtimes need the system PostgreSQL client library (`libpq`) before installing OAM. The local development dependency group installs the self-contained Psycopg binary extension; release installations omit that group. The release image must retain the system library's license notice.

## 1. Configuration

All chunk settings live under `chunk`: `chunk.ingestion` splits each message or document into passages with a 2,048 estimated-token target, 4,096 maximum, zero owned overlap and 128 prior context-only tokens. These passage limits apply to singleton and grouped extraction. `chunk.recall` holds the separate 8,192-token budget for the reserved `include.chunks` response option, which is not yet served; it does not affect indexing. Operator overrides use these nested paths, and capabilities publish them under `limits.chunk.ingestion` and `limits.chunk.recall`.

Message grouping is enabled by `extraction.group_max_passages: 64`. A short eligible source uses one extraction call when its complete serialized input and estimated output fit the configured bounds; longer sources split into source-ordered groups without crossing an ineligible message. Set the value to 1 for singleton extraction. `extraction.group_max_estimated_output_tokens: 4096` bounds the group planner estimate, while `extraction.max_output_tokens: 64000` caps actual extraction and Insight generation completions. Raising the completion cap does not enlarge groups because planning uses its separate budget. Length-truncated responses trigger recursive split-and-retry at passage boundaries, then within a singleton source span near a sentence boundary. Truncated content is never published. Unsplittable overflow remains a failure; malformed JSON and other provider failures do not trigger splitting. Each child rechecks cancellation and source eligibility and renews its fenced lease before dispatch. Resource vision and abstract completions remain capped separately by `resource.max_output_tokens: 4096`. Child calls run in source order under the existing outer checkpoint, and their usage is aggregated with overflow attempts; incomplete split trees are retried as a whole. Changing these extraction settings changes the indexing generation; an existing collection needs a separately authorized rebuild before switching, and startup does not clear its data. The default reduces calls for short sources, while real-model coverage, generation tokens and phase 1 latency still require evaluation.

Existing-fact extraction context is enabled by default alongside message grouping: `extraction.reference_max_facts: 10` allows up to ten facts, and `reference_max_input_tokens: 2048` is a configurable soft estimated-token target. The worker freezes complete eligible candidates and derives one proportional text preview for the extraction request. All text lengths use the same ratio after serialized metadata is accounted for; no short-first reservation or quota redistribution applies. Previews end at a nearby sentence or comma boundary, so the reference total may exceed the target. Shortened previews carry `text_truncated: true`, preserve IDs, speaker roles and time metadata, and remain incomplete context whose missing qualifiers are unknown. Stored facts and the complete new source are unchanged. `max_input_tokens` still hard-bounds the entire serialized model input; reference admission retains a prefix of relevance order without skipping a large higher-ranked record to fill with lower-ranked ones. Set the fact limit to 0 to disable reference context. Selection reuses passage embeddings and adds no generation call. Changing reference settings or the indexing recipe changes generation; existing collections need an explicitly planned rebuild. Quality gains and phase 1 time require matched real evaluation. Report embedding tokens separately.

`configs/oam.yaml` owns authentication mode, limits, role aliases, retrieval/profile policy, worker concurrency, leases, and retention. An alternate operator YAML may override selected fields; omitted fields come from the canonical YAML, never a second set of Python numeric defaults. At CLI startup, inherited process variables take precedence and `./.env` fills only missing variables. Environment variables supply the PostgreSQL DSNs, the private `OAM_ROOT_API_KEY` value when operator-supplied, model identifiers selected through `model_env`, model endpoint/key values referenced by the selected binding, operator secret-handoff destinations, and an optional alternate config path. An environment variable never overrides a behavioral default invisibly.

Required v0.0.1 roles are extraction, Insights, embedding, Resource abstract, and Profile generation. The extraction binding supports both chat and vision for text facts and visual document details; preflight checks both capabilities and fails the role if either probe fails. The canonical generative roles select `indexing_low`, and embedding selects `embedding_default`; endpoints, credentials and model names come from the referenced environment variables. `index.embedding_dimensions: 1024` owns the vector size used by database initialization and runtime validation; the endpoint must return that size. An unauthenticated embedding endpoint can set `models.bindings.embedding_default.api_key_env: null` in its operator YAML. Reranker and planner are optional. Each binding declares `protocol: openai_compatible`, exactly one of `model` or `model_env`, an endpoint environment variable, an optional key environment variable, and capabilities; preflight verifies the role-specific behavior rather than trusting a provider name.

## 2. Commands

- `oam preflight` resolves configuration, redacts secrets, and tests enabled role capabilities.
- `oam migrate` applies versioned PostgreSQL migrations with a separate migration credential.
- `oam api` runs the FastAPI role, bundled Inspector and, by default, an embedded background runner. Embedded mode requires the queue and worker-content DSNs in addition to the API DSN. Set `worker.embedded_enabled: false` for API-only processes.
- `oam worker` runs the same background processors with separate queue/content database roles. `--once` processes at most one queued work unit and exits. Each runner has up to `worker.max_tasks` concurrent tasks; per-user claims, generation, embedding and indexing DB transactions have independent limits. The embedded flag does not disable an explicitly launched worker.
- `oam model-permits --config <operator.yaml> list` inspects unresolved model-call metadata using the migration DSN's operator authority. API and worker credentials cannot directly update permit records.
- `oam model-permits --config <operator.yaml> reconcile <permit-id> --reason <text> --known-completed` releases a permit after independently confirming remote completion. `--force-unknown` instead acknowledges unresolved remote work and leaves physical concurrency explicitly unverified.
- `oam model-permits --config <operator.yaml> configure` applies changed YAML capacity values after APIs and workers have been stopped. Active HTTP ownership and live/uncertain model permits block the change.
- `oam recover-bootstrap` uses separate administrative database authority to replace a committed bootstrap key whose one-time handoff failed.
- `oam validate-export <directory>` checks a downloaded format-1 manifest, every declared JSONL part and original, counts, hashes and source/support identities without a database or model.

## 3. Bootstrap and Credentials

The operator initialization step is `oam migrate`, before starting API or worker replicas. Before applying migrations 0017–0021, drain and stop older API and worker processes, run `oam migrate`, then start the new version. Older workers cannot process dependency-bearing Profile jobs from 0018 or write the plural Insight subtypes required by 0020; the new API requires publication time from 0019 and Profile document columns from 0021. With `auth.mode` omitted and neither `OAM_ROOT_API_KEY` nor `OAM_BOOTSTRAP_OUTPUT` set, a fresh database gets the active `default` tenant without a root credential; `oam api` selects `dev` and must bind to loopback. Explicit rootless `trusted` mode also creates that default tenant and accepts local gateway identity headers; nonlocal trusted startup requires an active root key. `OAM_ROOT_API_KEY` stores an operator-supplied root secret as a database digest without writing a handoff file. Alternatively, `OAM_BOOTSTRAP_OUTPUT` names a new operator-only file for a generated root secret; the identity commits before the secret is written once with restrictive permissions, never ordinary logs. Exactly one bootstrap process wins, and interrupted generated-secret handoff requires explicit recovery. An empty root-secret value or simultaneous supplied secret and handoff destination fails. Existing keyed databases keep `api_key` mode when mode is omitted and never silently downgrade to `dev`; incomplete bootstrap fails startup. Application replicas receive only their separate runtime-role DSNs. The administrator creates a user through `POST /v1/users`, receives its first user key once, and uses that key for personal data calls; the root credential itself cannot use personal routes in `api_key` mode.

Positive credential verification may be cached for a fixed non-sliding 30 seconds under the full supplied-secret digest. Invalid keys are not cached. Revocation commits first, prevents an older lookup from repopulating the cache, and reports the maximum cross-process propagation deadline.

After an interrupted `committed` handoff, rerun `oam migrate` to record `recovery_required`, then explicitly run `oam recover-bootstrap` with a new recovery destination. Recovery commits revocation of the lost key and issuance of its replacement before handoff. A further interruption again requires explicit recovery; it never silently creates another administrator.

## 4. Limits and Failure Ownership

The Profile model call has its own 180-second timeout in `profile.attempt_timeout_seconds`; the worker extends only that Profile claim lease for the call, while refresh returns a durable receipt before generation. The first supported workload limits each Resource to 20 MiB, 20 PDF pages or images, 40 megapixels per image, and 100 megapixels total; each tenant/user pair supports 100 reports and 1,000 chats in the trial profile; the deployment admits 10 simultaneous API requests. An HTTPS Evidence URL has the same 20 MiB content cap and a 30-second total fetch deadline owned by `resource.url_fetch_timeout_seconds`; DNS, connection and body transfer share that deadline. Local PDF parsing/rendering has a separate 30-second child deadline owned by `resource.pdf_child_timeout_seconds`, plus a bounded result transfer. Inputs exceeding bounds fail before parsing or model dispatch.

The canonical capacity defaults are:

| Setting | Default | Scope |
|---|---:|---|
| `api.max_concurrent_requests` | 10 | Shared admitted business HTTP requests across replicas |
| `api.max_concurrent_writes` | 6 | Shared mutating requests; four total slots remain available to reads |
| `worker.max_tasks` | 10 | Tasks per runner |
| `database.indexing_concurrency` | 4 | Shared indexing transactions across replicas; model I/O holds no DB slot |
| `user.concurrency` | 2 | Live claims per tenant/user across all runners |
| `queue.max_pending_per_user` | 1,000 | Unfinished root intake requests, including delayed required children |
| `provider.llm_concurrency` | 32 | Shared text/vision generation calls |
| `provider.embedding_concurrency` | 8 | Shared embedding calls |
| `provider.embedding_search_reserved` | 0 | Optional embedding capacity withheld from background work; search may use any free slot |
| `provider.rerank_concurrency` | 4 | Local reranking calls per foreground model client |

HTTP admission covers `/v1/` routes; liveness/readiness and static assets remain accessible without consuming those business slots. POST search is a read for admission. Overload returns retryable `429` with `Retry-After` before body consumption or source acceptance. Each admitted HTTP request holds a separate PostgreSQL session for its admission slot; include up to ten such sessions deployment-wide and short model-admission transactions in database connection planning, in addition to content pools. Runtime DSNs must connect directly or through session pooling; transaction pooling cannot preserve session advisory-lock ownership.

The first API or worker startup freezes shared capacity settings in PostgreSQL. Replicas with conflicting shared limits fail startup. Operator YAML uses independent generation, embedding, worker-task and indexing-transaction limits; obsolete `worker.max_model_calls`, `database.worker_pool_max` and `provider.global_concurrency` keys must be removed. To upgrade an existing deployment to migration 0023 or change shared limits: stop API and worker processes, resolve uncertain permits, run `oam migrate`, run `oam model-permits --config <operator.yaml> configure`, then restart every replica with matching settings. The configurator rejects active model permits, HTTP admissions and indexing transaction slots. Numerical defaults are initial capacity settings; they are not a throughput or latency guarantee.

Intake admission checks idempotency before the root count. Running work, automatic retries and delayed consolidation keep their root slot; an explicit retry needs a new slot. Exact receipt reuse and unchanged Profile refresh still work at the intake cap. Source-deletion cleanup is exempt so that a full intake queue does not prevent source removal. The URL path performs a cheap queue precheck before fetching and repeats the authoritative check when accepting bytes.

Model permits distinguish an unused reservation from committed dispatch intent. Unused reservations may expire; dispatched calls with unknown outcomes remain occupied after timeout, cancellation or process loss. Each model permit ID is sent as `X-Request-ID` to the provider for correlation. Inspect unresolved permits with the operator command and confirm remote completion before release. A fully uncertain pool is visible as blocked in readiness. An explicit forced release preserves the uncertainty record and cannot prove a physical remote-concurrency ceiling.

The worker preserves compatible checkpoints and usage before dependent work. Shutdown stops claims and new model dispatches, waits up to `lease.shutdown_seconds`, and reports incomplete drain when synchronous work survives. Clients remain owned by those tasks until their final completion; a timed wait does not forcibly terminate a Python thread. Work leases, fences and unknown-outcome accounting remain authoritative for recovery.

The API commits Resource revision or all-version source exclusion before returning an operation receipt. Deletion cancels outstanding indexing claims and queues a separate `cleanup_source` work unit; the worker removes affected active-store derivatives, original bytes and held export parts, then marks the cleanup operation succeeded. A failed cleanup stays visible as pending or partial failure and never restores eligibility. New recall, inspection, trace and export reads recheck current policy; an in-flight read that crosses a source change returns a named unavailable or redacted outcome. Backup expiry and restoration proof belong to the later release operations gate, so cleanup success describes the active PostgreSQL store only.

## 5. Current Implementation Status

The core adds eligible interaction and HTML indexing, supported L1/L2 publication and fast/mid/deep direct recall to the [foundation](foundation-evidence.md). Deterministic isolated-database tests also exercise uploaded and URL-fetched PDF/image Evidence, child PDF processing, citations and joint recall. Source/typed-Resource controls, stored L3 Profiles, recorded explain/replay, L3-aware portable export and the Inspector have isolated public-HTTP or browser checks. A separate API/worker probe with configured real models has exercised the earlier core path; live Profile generation quality, document vision and cross-language retrieval remain unverified. Progressive LongMemEval evaluation is underway and has not passed. Shared capacity admission and embedded/dedicated processing have deterministic coverage. Abrupt process-loss recovery, backup restoration and release-image gates remain. [Architecture](architecture.md) describes the current pipeline, and [acceptance](acceptance.md) defines the remaining gates.

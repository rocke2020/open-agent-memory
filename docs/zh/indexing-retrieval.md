# 索引与检索

[中文文档](README.md) · [English](../indexing-retrieval.md)

## 概述

OAM 保存合格的会话原文，抽取各自有证据支持的记忆，整合为有来源的洞察，并为调用方返回带引用的上下文。调用方负责最终回答。文档单独组成证据池。PostgreSQL 保存原件、派生索引、策略、操作和工作归属，无状态 API 和持久化工作进程共用这些信息。

本文描述 v0.2.1 的索引与召回设计。接口见 [API 参考](api.md)，设置见[召回配置](../../configs/README_CN.md)，验证范围见[验收](acceptance.md)。

## 1. 数据表示和权威来源

| 表示 | 含义 | 权威来源 |
| --- | --- | --- |
| L0 | 已接收的会话原文及段落 | 不可变来源版本和原始字节 |
| L1 | 分别具有标识的学习事实、偏好及经历 | 合格 L0 中的准确引用 |
| L2 | 在合格 L1 基础上生成并保存的洞察 | 当前支持事实标识、版本及 L0 来源 |
| L3 | 一份有来源的持久化用户画像 | 合格学习输入和用户声明的画像资料 |
| 证据资源 | 文本、HTML、PDF 或图像原件、抽取段落和生成摘要 | 当前不可变的文档版本 |
| 画像资料 | 所有者声明的结构化字段 | 已注册子类型及当前不可变版本 |

每个派生记录都关联来源版本、索引代次和租户及用户身份。向量维度相同仍需确认语义空间兼容。资源摘要属于证据层。证据资源与学习记忆和画像输入分离。宿主负责声明保留的消息是否允许学习，包括基于文档生成的助手回答。

## 2. 接收与持久化工作

1. 通过身份认证确定租户和个人权限，校验用户、输入模式、限制和已启用的能力，并应用幂等规则。
2. 调用外部模型前，提交已接收的原始字节、来源版本和操作回执。回执区分接收、来源可搜索、L1 就绪和 L2 就绪。
3. 工作进程通过 PostgreSQL 领取有界工作，记录所有者、租约及单调递增的栅栏值。远程调用在数据库事务外执行。
4. 每个完成阶段发布前重新校验来源版本、代次、资格、取消状态和当前所有权。失去所有权的进程不得发布或将用量记入当前工作。
5. 输入身份相符时复用完成的阶段。保留外部结果不明的尝试并显式核对，避免盲目重放可能已计费的请求。

API、队列和内容分别使用非所有者角色，强制行级安全策略。应用重启会保留已接收的原文及持久化回执。插件在后端接收前的自动采集仅在宿主进程内处理，退出进程可能丢失尚未接收的输入。

## 3. 会话索引

索引选出可学习的消息，保留 L0 段落，按确定性规则分块，并以有界分组抽取各自有证据的 L1 条目。抽取时可以读取少量先前的 L1 参考以维持上下文，但新陈述始终需要当前原文支持。引用文本和范围校验把学习内容绑定到原始消息。实体识别保留原始名称、经原文证实的别名及来源段落，同时区分反复出现的同一身份和同名对象。

分组完成后计算其向量，并与实体归属、有向关系和时间证据逐步发布。时间与语义关联任务遵循相同的资格和发布规则。状态显式记录进度与部分覆盖。后续阶段失败时，先前已就绪的阶段仍可独立使用，整体状态保留后续失败。

可选的单来源生成预算启用时，会在发出抽取和洞察调用前预留用量。默认不启用该预算。输入、输出、推理和失败或重试用量都记录为生成用量，向量用量单独记录。输出上限参与预算预留，实际消耗取决于响应。评估预算与阶段就绪还需要实际用量和状态。

## 4. 洞察整合

L2 将有用且相互支持的 L1 事实整合成更长期的记忆。可在 L1 完成后启用 L2，并复用已有 L1 索引及原文。就绪来源进入固定时长的单用户整合窗口，默认 24 小时。功能测试可在隔离环境缩短窗口。

种子策略选择有界的合格 L1 输入。在已有洞察中查找更新目标时，词法部分在当前索引代次内使用逐词 FTS。公开召回的词法排序设置不影响此查找。[洞察目标查找](../../src/oam/indexing/consolidation.py)模型可返回有来源支持的新增或更新，也可返回有效的无洞察结果。格式错误、空响应、拒答和运行失败分别处理。发布时核验支持及其当前版本，更新复用原洞察标识，并记录描述性子类型。支持 ID 验证来源关系。多条改写同一事件的事实仍只反映一次事件。

每条洞察有一个易读的长期主题标题。CREATE 和 UPDATE 提供非空标题，最多 120 个字符。只有证据改变或明确了主题时才更改原有标题。事件日期、交付历史和临时状态通常写在正文。仅更新支持时标题原样保留。因支持被移除而完整修复时，从剩余证据生成标题，主题名称可能改变。标题保存在检索单元的展示元数据中，随记忆检查与导出返回。独立的检索标签仍用于向量表达。既有记录使用保存的主题标签或有界正文预览，不需要生成或重建索引。

新的合格学习输入可以改变 L2，并使已有画像过期。可按用户配置[画像定时刷新](profiles.md)，所有自动触发默认关闭。来源排除及精确移除会先使相关支持失效，后续工作进程无法再发布依赖这些支持的内容。

### 自动整合窗口

自动整合按租户、用户及索引代次收集就绪来源。首个接收时确定固定截止点，默认延迟 24 小时。之后的来源严格早于截止点才能加入。在截止时刻或之后抵达的来源进入下一窗口，即使工作进程延迟开始。使用 `related` 种子策略时，可在一次有界请求中合并多个成员来源的相关新事实，未合并或放不下的事实继续待处理。历史支持事实可提供背景，保留原有完成状态。

窗口持有冻结的分组输入和已保存响应，各来源仍各自管理就绪状态与生成预算。按序列化新种子字节分摊共享调用额度，使用确定性的整数舍入并保持总量，然后原子地从每个参与来源的上限预留。各来源的限额不能互相借用。分组失败或未完成时保留已成功工作，外部结果不明的尝试仍需核对。部分成员可先进入 L2 就绪。

仍支持原有的按来源整合和移除后的修复。支持新批处理阶段的新版工作进程才会领取批任务，两类阶段共用按用户 L2 领取与暂停边界。显式从已有 L1 触发索引时立即安排处理，限制来源数，并跳过已有分配的来源、版本及代次。画像刷新等待共享批依赖，同时保留失败输入和移除修复的检查。已测范围见[发布验证（英文）](../releases/0.2.0.md)。

## 5. 证据和画像

证据接口接收已声明的文本或支持的 HTML、PDF、图片原件，在 PostgreSQL 保存原始字节，按页、区域或块定位抽取段落，并生成有引用和来源资格的摘要。原生 PDF 抽取与基于视觉的文档处理分别运行，分别记录就绪和失败。原件可供独立核对 OCR 和摘要。

证据可参与普通召回。L1、L2 和 L3 有独立的数据路径。更新资源时检查预期版本。删除立即排除所有版本，并排队清理存储。画像资料根据已注册子类型精确映射到对应字段，并有独立生命周期。

`GET /profile` 读取存储内容。显式刷新在输入身份一致且合格时以零调用复用，否则创建持久操作。创建或刷新先处理未就绪的会话输入，复用运行中任务，根据现有重试约束对每个失败的原始任务至多重试一次，并推进已排队洞察。画像任务会等待初始索引和随后排队的洞察，再生成内容，并复用兼容的已完成检查点。重试额度耗尽或外部结果不明需要运维处理。成功结果包括有来源支撑的内容及引用。失败刷新时保留先前仍合格的内容，来源状态变化也可以独立使先前支持失效。精确画像资料具有自己的引用和权威来源。

[资源实现](../../src/oam/resources/) · [画像实现](../../src/oam/profiles/)

[画像调度和自定义生成](profiles.md)介绍个人画像策略及临时 `POST /profile/generate`。自动刷新复用[持久化画像接收](../../src/oam/profiles/scheduling.py)及已有工作进程。[自定义生成](../../src/oam/profiles/generation.py)用完整指令选择证据，返回校验后的内容和引用，不存储自定义画像或输出。两条路径都遵循已有证据资格、授权及 token 限制，并与普通召回分离。

## 6. 候选检索与排序

API 在校验所选模式的覆盖设置、选择预算、分解计划请求和发起检索前，先确定生效模式。显式指定的 `recall_level` 优先。请求省略该字段时，使用 `search.default_recall_level` 配置的 `fast`、`normal` 或 `deep`，默认 YAML 和请求模式均采用 Fast。直接、批量和规划召回使用相同优先级。Inspector 初始选择 Fast，每次显式提交界面选择。随 v0.2.1 提供的 MCP、OpenClaw 和 DSH 接入归档在工具调用未指定模式时也会显式发送 Fast。[召回处理](../../src/oam/api/search.py) · [请求契约](../../src/oam/contracts/search.py) · [默认配置](../../configs/oam.yaml)

召回采用一份绝对截止时间，并用完整原始查询计算语义向量。显式日期窗口优先于确定性的查询时间解释。窗口影响时间排序，其他检索通道找到的合格证据仍可来自窗口外。当前来源策略和租户、用户权限严格限制资格。

Fast、Normal 和 Deep 共用直接向量、一个词法通道，以及可选的时间和个人证据通道。每个模式分别设置 `entity_semantic_graph`。`"off"` 关闭实体和语义图扩展，`light` 通过共同实体 ID 扩展，`full` 也沿已保存语义链接扩展。Fast 默认 `"off"`，Normal 和 Deep 默认 `light`。三种模式共用 `search.causal_graph`，默认 `false`，独立控制出向因果遍历。各已执行通道通过倒数排名融合，随后可按配置重排。[图扩展配置](../../configs/README_CN.md#1-图扩展模式) · [召回服务](../../src/oam/retrieval/service.py)

v0.1.0 的词法通道将 PostgreSQL 覆盖密度（`ts_rank_cd`）与准确引用短语和标识符匹配合为一次融合投票。Fast 和 Normal 的词法排序和相邻用户上下文各自配置。Fast 可在来源校验和局部证据选择后为合格候选打分，Normal 在配置重排时较早为已加载候选打分。[v0.1.0 配置指南（英文）](https://github.com/rocke2020/open-agent-memory/blob/v0.1.0/configs/README.md)

请求包含正文且 `personal_evidence_candidates` 为正数时，使用已有查询向量在用户段落中检索当前 L1 偏好或经历的支持原文。段落必须与当前来源版本一致，并通过支持校验。常规向量通道已召回的原文只计一次向量票。新增命中仍适用常规融合、重排及上下文预算。合格原文可以通过自己的局部证据检查。助手回复的见证及图扩展种子仍来自普通向量结果。该通道复用已有证据及查询向量。[个人证据配置](../../configs/README_CN.md#8-个人证据候选) · [候选资格及排序](../../src/oam/retrieval/repository.py)

局部证据是与候选属于同一来源版本、由用户原文支持的独立事实。部分匹配筛选可要求此证据，再接纳间接发现的会话原文或助手回复。直接向量、严格词法命中、完整洞察支持和证据资源各有独立资格。词法候选短名单中的用户原文可直接参与。该短名单中排名最高、已取回正文且合格的用户或助手消息也可参与，包括以助手消息开头的会话。排名第一的用户原文占用这项例外，排名较低的助手原文仍需现有独立或局部证据。这些例外保留相关性顺序及预算，不能为派生事实、相邻回复或来源扩展提供新的见证。

启用相应筛选时，补充用户原文在按查询相关性排列、受 `source_seed_results` 限制的同一个池里竞争，已缓存和未加载的正文都可参与。池中不纳入已独立排序的原文或各来源版本已选独立用户事实的必需正文。其余缓存原文仍可入选，已加载不代表对应事实支持组一定能放入预算。复用已取回的正文，只加载一次其余入选正文，并保留原引用和检索路径。补充原文仅依附现有独立事实，没有额外融合票，也不能成为新事实见证或扩展种子。渲染预算和身份去重保持适用。

三种模式都用 `source_seed_results` 独立限制来源发现，包括为间接助手回复提供见证的向量结果前缀，仍受通道候选上限约束。`max_results` 分别限制最终学习条目和原文的数量。调小此值不缩小来源发现、必需支持或回复见证预算。在选中来源版本内，补充用户原文恢复先物化合格的单元标识及向量，再在候选限制内按精确余弦距离排序。同距离以单元 ID 决定顺序。来源、版本、归属、角色和生命周期筛选在候选池内生效。全局向量检索有独立的近似搜索路径及扫描预算。恢复受请求期限限制。[召回服务](../../src/oam/retrieval/service.py) · [候选查询](../../src/oam/retrieval/repository.py)

各预设拥有自己的 `temporal_nodes` 遍历预算，包含种子和后续节点，Fast、Normal 和 Deep 默认为 64、200 和 300。直接时间命中单独接收，最终结果池由 `max_results` 限制。单次请求可通过 `overrides` 覆盖选中预设和部分通用设置。例如 `{"recall_level":"fast","overrides":{"temporal_nodes":300}}` 让 Fast 的遍历上限为 300。检索 I/O 前校验合并后的设置，直接、批量和规划路径均将其应用于数据库检索、可选重排和上下文组装，批量查询分享覆盖后的总预算。`diagnostics.search_config` 记录生效预设和共享覆盖。[时间遍历和请求覆盖](../../configs/README_CN.md#7-时间遍历预算与请求覆盖)

普通召回不调用生成模型。批量查询共享一次模式总量和期限。显式启用的规划器可在独立步骤生成查询计划，然后仍通过普通召回获取结果。

### 按所有者统计的 BM25 与共享召回设置

召回以 PostgreSQL 全文搜索匹配候选，用带字段权重的 BM25 加两倍 PostgreSQL 覆盖密度分数对普通命中排序。BM25 利用词项在该用户索引中的稀有度并考虑文档长度。覆盖密度为彼此接近的查询词加分。严格全文和主词项匹配优先，受保护的引用短语和编号标识符使用文字精确匹配，只有功能词时使用已有 FTS 回退。三种模式的 `search.lexical_ranking` 默认为 `whole_query`，排序一份候选列表，可用 `per_term` 分别排序各词项列表再融合。[词法实现](../../src/oam/retrieval/repository.py)

BM25 统计按租户和用户统计已物理索引的单元。词法项插入、替换或物理删除时，PostgreSQL 在同一事务更新倒排项和统计。读取用当前统计评分。已撤回和被替代的来源立即不能召回，在物理清理时移出统计。迁移 0040 利用已有词法字段构建投影，无需重新抽取或计算向量。[词法投影迁移](../../migrations/0040_bm25.sql)

11 月 22 日的 LME-500 结果通过评测适配器在保留的索引上采用 BM25 加覆盖密度，在 8,000 tokens 的 Fast 上限下获得 476/500。v0.2.1 默认 `search.lexical_ranker: bm25`、`search.fast.context_max_tokens: 8000`。评测复现使用固定的适配器与索引状态。[评测设置](benchmarks.md#1-longmemeval-s-的-8k-与-18k-结果) · [默认配置](../../configs/oam.yaml)

三种模式共用 `search.partial_match_gate`，默认的 `user_fact_exchange` 在组装前筛除证据较弱的会话候选，设为 `"off"` 可关闭。当请求包含正文时，三种模式均可在已入选的普通事实附近附加已发现的相邻用户原文。`search.adjacent_user_context` 默认启用，`search.adjacent_user_context_max_chars` 默认每段可选相邻原文最多 1,000 个字符。

Fast 按融合相关性选择上下文。Normal 和 Deep 可用可选的 `models.reranker` 对已加载正文的候选评分，随后验证来源支持、组装上下文。各自的 `rerank_candidates` 限制评分批次，默认 48。[来源正文与重排](../../configs/README_CN.md#6-来源正文与重排)

## 7. 上下文组装

三种模式共用 `search.fact_source_bodies`。默认 `required` 依照下面的完整证据组规则。实验性的 `ranked` 将已校验的引用支持与完整原文分开竞争预算。普通事实保留完整文字、准确引用、来源和时间。每份完整原文，包括恢复出的合格项，都须作为独立的最终候选取得位置。仅用于来源详情或附在事实后的可选正文不占独立位置。入选正文保持完整，完整洞察和证据资源保留其必需支持。去重比较完整且已校验的支持。当原文仅能作为事实支持时，此策略可能省略有用的未引用内容。诊断会记录有效策略。

实验性的 `assistant_deduplicated` 先进行普通的完整证据接收、生命周期检查和 token 裁减，再只移除完全满足条件的事实。该事实由助手消息支撑且未截断，已选入完全一致的完整原文，时间证据完全相同，而且事实本身无检索路径。保留所有原文、由用户或混合或未知来源支持的事实，以及必需洞察支持。策略保留接收顺序和条目顺序，不添加替代候选，若精确 token 数反而增加则回退到完整渲染。仅在包含正文时适用。`diagnostics.context_budget.assistant_deduplicated_fact_ids` 列出移除项。准确率须通过评测验证。

实验性的 `ranked_deduplicated` 使用 `ranked` 接收。在准确位置及唯一引用校验通过、完整时间证据一致且普通事实无检索路径时，用已经入选的完整原文代替该事实，原文保留来源组相关性位置及完整正文。找不到匹配原文、原文不完整或有截断、时间不同或者有检索路径的事实保留。洞察支持保持完整。两个结果池都在替换前计数，只回收渲染 token 空间。最终根据来源状态重建时也执行相同判断，移除原文候选会恢复不再匹配的事实并重新检查预算。诊断列出替换项。更低的 token 数需与实测准确率一起评估。

候选按相关性优先、时间新旧其次排序，并按此顺序接收完整组。洞察组包括必需的 L1 支持和原始引用。学习条目和原文分别受结果池数量限制，最终共用一个完整渲染预算。引用元数据及重复引用都计入预算。

相同的完整时间元数据可以共享上下文内的 `Time Tn: ...` 定义和 `Time: Tn` 引用，并先应用来源时间继承。保留正文、引用、时间角色、事件范围、精度和时区。结构化项保留原始元数据。只有包括定义的完整渲染确实更省 token 时才共享，定义也计入同一预算。

Fast、Normal 和 Deep 的默认总预算为 8,000、16,000 和 24,000 tokens。`context_tokens` 使用本地 `o200k_base` 统计完整返回文本。宿主用自己的回答模型分词器另算完整输入。完整上下文超过宿主上限时，插件会拒收或省略该响应。

`include.chunks: false` 省略原文全文，同时保留合格学习内容和真实引用。启用正文时，必需支持先于可选邻居。节选保留来源身份，不授权进一步扩展。完整原文后来满足全部渲染空间时可替换节选。

上下文预算适用于每个完整证据组，包括单条 L1 事实及其支持。放不下的整组跳过，之后较小的组仍有资格入选。每个返回项保留带类型的来源、规范标识、引用及适用的时间或图路径。调用方使用证据推理并生成答案。

## 8. 生命周期、移除与恢复

精确 L1 移除接收一个规范记忆 ID，立即排除该条目及受影响的依赖洞察，并返回独立的清理或修复回执。精确 L2 移除接收一个规范洞察 ID，保留支撑事实和原文。移除请求不调用生成模型。后续经授权的整合由独立操作处理。已提交移除无法撤销。

来源删除排除该来源，以及当前资格规则下依赖它的学习内容、证据、画像、跟踪和导出视图。资源或画像资料修订使用预期版本，保留不可变历史标识，并以新活跃版本为准。返回或发布前重新检查资格，旧工作进程、快照和缓存无法重新提供已撤回内容。无关活跃来源保持可用。

多个 API 副本和工作进程共用 PostgreSQL 的所有权状态及原件。本地发布验证针对应用中断和重启、队列恢复及滚动替换。数据库高可用、独立机器故障及模糊写入的透明重放需要单独验证。

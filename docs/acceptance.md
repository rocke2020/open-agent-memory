# Open Agent Memory Acceptance

## Overview

Release claims require fail-capable evidence through the real public path. Unit tests prove deterministic policy, integration tests prove PostgreSQL/provider boundaries, and a small authorized end-to-end run proves the inspectable artifact; one layer never substitutes for another.

## 1. Steps 1–4 Foundation Gate

The foundation gate requires a clean focused package, self-contained public documents, closed configuration, versioned migrations/RLS, credential/bootstrap behavior, durable operation/work claims, bounded local parsers, model capability probes, OpenAPI DTOs, operation routes, conformance fixtures, and a same-origin Inspector shell. It explicitly does not claim indexing or retrieval.

The repository records deterministic unit/contract coverage and PostgreSQL integration coverage for this foundation. Integration tests are skipped unless both `OAM_TEST_POSTGRES_DSN` and `OAM_TEST_POSTGRES_ISOLATED=1` identify an explicitly isolated database. Bootstrap tests create separate databases on that isolated server and retain them for diagnosis; the test operator needs database-creation authority. Current foundation evidence includes a real PostgreSQL 18 run, but does not establish production deployment or replica recovery.

Authentication acceptance requires an isolated API/SQL matrix for `api_key` root denial, same-user and cross-user keys, rootless `dev` loopback startup and keyed-database downgrade rejection, plus `trusted` local assertions, first-seen user registration, tenant/user mismatches, nonlocal root-key proof and root-only administration. A candidate nonlocal trusted deployment must separately prove that its gateway authenticates callers, replaces spoofed identity headers and blocks direct listener access; application tests alone cannot pass that deployment gate. OIDC and LDAP are outside v0.0.1.

The dated commands, artifact probe, and explicit exclusions are recorded in [Steps 1–4 foundation evidence](foundation-evidence.md).

## 2. Step 5 Core Indexing and Recall Gate

This gate evaluates interaction indexing and recall independently of Resources and L3 user Profiles. The public path must commit eligible conversations and receipts, produce source-supported L0/L1/L2, and return cited Memory through direct fast/normal recall. Prove the public fast path first, then complete normal within the same gate.

Both modes use one pipeline and resolve supported query dates before candidate retrieval when no explicit ranking window is supplied. Canonical fast fuses dense, one FTS-plus-narrow-literal lexical arm and optional temporal. Both modes independently configure entity/semantic graph selection and causal traversal, sharing one optional graph arm for at most four fusion arms. The canonical normal configuration weights graph at 0.1 and its other executed arms at 1.0. Fast gives its executed arms equal weight. Verify through public HTTP that `LAB-204` does not match `LAB-2045` and an intentional `"morning shift"` match is contiguous; mixed identifier and quoted-phrase queries must rank exact matches by their remaining informative words before the cap, while an ordinary name made only of filtered function words must still receive strict lexical search. Inspect fusion inputs to prove that a unit found by FTS and literal matching receives one lexical vote and no `anchors` arm reaches RRF. Verify bounded partial-match candidates across varied topics and query wording without topic-specific vocabulary, plus source evidence in both fast and normal answer contexts under the configured item and estimated-token budgets. Verify bounded entity/semantic links and independently enabled two-hop causal paths: turning causal off must preserve temporal links and date filtering, while turning entity/semantic off must still permit configured causal-only retrieval. Verify all four combinations through actual recall contexts, with disabled SQL branches omitted before candidate caps. Verify English, Chinese and supported Japanese absolute/relative expressions, explicit-window precedence, ambiguous-date diagnostics that preserve ordinary recall, timezone boundaries, and out-of-window direct evidence remaining eligible plus a graph-only temporal discovery through public HTTP. Verify configured reranker calls and non-degraded RRF-only behavior when absent for normal; fast always skips reranking. Require a generated, persisted, retrievable L2 Insight with one validated descriptive subtype and exact L1-to-L0 support, incremental synthesis, and distinct valid `no_insight` versus malformed, empty, refused, or failed outcomes. No recall mode may generate content; each must enforce its request/shared-turn deadlines and disclose failure or partial coverage. Both modes must be verified through the public API before this gate passes. Progressive LME-6, LME-30 and LME-60 evaluations remain required; the small functional probe is not a benchmark gate.

Verify the configured local-evidence policy through actual fast recall: a direct user fact and its exact user original within the configured dense seed prefix can retain a partial-match assistant reply from that exchange, while an unrelated later turn in the same source does not inherit the witness. Preserve direct dense and strict lexical/literal hits, configured graph results, Resource results and complete Insight support. Verify per-citation original pairing, source-version isolation, raw dense ordering before witness filtering, and the separate whole-query versus per-term lexical policies. Verify unavailable dense retrieval preserves degraded lexical recall. Check an independently unextracted adjacent user original reaches the answer context after its fact, with whole-body accounting and no fabricated citation; an oversized neighbor must leave the required fact/support intact. Verify bounded recovery of earlier user originals beyond the adjacent window from exact independently matched user-fact sources, across varied topics. Weak lexical facts, assistant-only sources and other source revisions cannot authorize this recovery; recovered originals cannot authorize assistant replies or further expansion. Required owner support precedes supplemental originals, and an omitted owner leaves the original eligible at its ordinary candidate position. A complete recovered original can upgrade an earlier excerpt only when the full rendering fits; an over-budget upgrade preserves the excerpt and required support. Inspect final coverage, displaced later evidence, complete-original counters and unrelated context together. Keep the original query embedding, graph choices, deadlines and 64/128/36/96 fast limits unchanged, and measure complete repeated HTTP latency alongside context relevance.

Verify fast's 18,000 and normal's 32,768 complete-rendering defaults and isolated 2,048-token caps in both modes. Omitted `include`, empty `include` and `chunks: true` must include eligible full bodies; strict `chunks: false` must omit all full-body items/blocks, including Insight sources, while retaining eligible learned items, every required supporting fact and genuine citations. Reject null/nonboolean options, old chunk-options objects and removed request budgets. Recompute full rendered counts including metadata, repeated quotes and separators. Check whole-bundle omission without clipping, the sole eligible L1 fact fallback returning its complete oversized bundle alone only when no higher-ranked root was admitted, explicit overshoot diagnostics and no subsequent filling, no Insight exemption, shared-source deduplication, complete Insight support and per-pool result caps. Independently ranked answer-bearing originals with no extracted fact or an oversized learned bundle must retain their relevance position and complete text when they fit. Verify ineligible candidates cannot consume eligible source representatives before caps. Two-query batches share one mode total, and planned searches preserve the same boolean and mode contract. Inspect final returned evidence and citations, rather than only candidate presence or counters.

Index the fixtures once, then compare fast and normal on the same eligible index and query set, with the compared mode context caps recorded in configuration with L3 disabled. Expected facts/passages/support citations, including evidence reached by the graph arm, make the checks fail-capable. Retain requests/responses and fixture/config identity; report indexing usage once, per-mode retrieval quality against expected evidence, context tokens, recall usage, latency, and failures. Prioritize fast/normal quality and latency as the common real-use modes. Final-answer accuracy requires a separate external evaluator.

## 3. Step 6 Evidence and Joint Recall Gate

Use the public [synthetic bilingual fixtures](../conformance/fixtures/medical/bilingual/README.md): equivalent English and Chinese HTML, native-text PDF, scanned PDF and PNG reports, plus three-page text-only allergy reports with many rows. Retain each original through public HTTP, verify stored bytes and manifest hashes, extract detailed passages, generate an abstract and report measured vision usage. Native PDF pages must keep physical-page citations; the allergy reports must index every page without vision. Scanned pages and images must use the extraction binding's vision capability and cite the page or image plus a validated region when present. A vector-drawn table with native text must request visual structure while preserving the native wording. A failed later PDF page must leave only completed detail searchable with explicit `allow_partial: true`; abstract failure must not erase indexed detail. No report or abstract may produce L1/L2.

Retain eligible chat separately and run fast/normal against one combined index. Check a selected context containing both Memory and Evidence under one complete-context token cap and separate learned-item/original-body result caps, citations and source lineage, shared deadlines, zero generative recall calls, and report-derived assistant answers excluded from learning. Deterministic isolated-PostgreSQL tests prove routing and API contracts; an authorized live run with document vision and multilingual embeddings must verify actual English/Chinese extraction and opposite-language recall before model-quality acceptance. Keep requests, receipts, citations, usage and fixture/config identity as inspectable evidence.

For URL Evidence, run one isolated deterministic HTML, PDF and image URL through public retain, worker indexing and cited recall; compare the stored bytes and digest to the fetched original. Verify authorization before fetch, identical-key reuse without refetch, failed-fetch retry, nonpublic DNS/literal IP rejection, pinned checked address, redirect rejection, bounded transfer, mismatched-media rejection and query-token redaction. A 200 HTML page declared as HTML is accepted as returned and needs caller inspection. Before release, untrusted local PDF parsing and rendering must run in a bounded child process; a stalled or crashed child must not hang or crash the durable worker.

## 4. Step 7 User Profile Gate

Step 7 implements L3 user Profiles on the evaluated core: stored `main`, `preferences`, and `experiences`, eligible L0/L1/L2 and explicit Profile Data inputs, dirty-but-not-automatically-generated behavior, read-only `GET`, asynchronous changed-input refresh, and unchanged `200` reuse with zero generation calls. Verify User Profile exclusion of report-derived content and preservation of still-eligible prior fields after failed refresh.

The agent-integration scenario starts with host-run fast recall before the agent invocation. During the ReAct loop, the agent can request any of fast or normal again. The HTTP contract must preserve the chosen mode and never perform an automatic escalation or impose a fixed sequence.

LongMemEval performance acceptance covers fast and normal only, in order LME-6, LME-30 and LME-60. Both modes must meet the declared four-metric gates on the same indexed histories.

Recall, batch recall and planned-search retrieval must remain independent of L3: reject the removed Profile-selection option, never access or attach the stored document, and preserve the full retrieval budget and relevant underlying facts. Verify recall with a stored Profile and a fail-on-read Profile accessor, then repeat retrieval with Profiles disabled while explicit Profile read/refresh report capability unavailable. Independently read the Profile, request a changed-input refresh, observe its successful operation and read the updated document. Preserve zero-generation reads, zero-call unchanged refreshes, whole-document budget omission and source eligibility rules.

## 5. Step 8 Source and Inspector Gate

Step 8.2 source lifecycle is independent of L3 User Profile implementation. Through public HTTP on an isolated user collection, retain two independent sources, revise text and uploaded/URL Evidence with `If-Match`, reject a stale version before expensive input work, delete a chat source and a revised Resource, and prove all versions disappear immediately from L0/L1/L2, Evidence passages/abstracts, recall, inspection, traces and export while the independent source remains available. Repeat deletion must return the existing cleanup receipt; a worker with a stale fence or old source version must not republish content. Run the cleanup claim and inspect its terminal operation, active-store originals/derivatives and held export parts separately from the immediate exclusion receipt. User Profile propagation is checked only after Step 7 in the serial integration gate.

Step 8.3 inspection requires authorized L1/L2 support and Resource original/locator views, recorded trace explanation, current-policy recorded replay and output diff, plus a downloaded export whose manifest and every declared member pass the offline validator. Challenge a deleted candidate, changed export policy, tampered checksum, missing support, root key, other user key and in-flight policy change. Browser acceptance covers the same public routes, inert rendering of source HTML, exact-target deletion confirmation, operation readiness, page-memory-only credentials, sign-out, focus/navigation, narrow screens and light/dark system preferences. A working shell or local deterministic probe does not establish real-model quality or release readiness.

## 6. Complete Release Gate

v0.0.1 extends the completed core, Evidence and L3 gates to batch/planner integration over the fast/normal core, source revision/deletion, explain/diff/recorded replay, portable export, browser/API parity, multi-API/multi-worker recovery, and external benchmark screening. The final candidate image is built for Linux AMD64 and ARM64 and the complete matrix reruns against its immutable digest before source/image publication.

LME-60 alone does not complete release evaluation. BEAM 10M is an additional required gate: index all ten official complete conversations and evaluate all 200 questions through public OAM fast recall using a versioned answer-generation and rubric-scoring protocol. Freeze input, evaluator, product, model and configuration identities; preserve source dates and the approved single date imputation. Disable Insights and Profiles only in the isolated benchmark configuration and use a 15,000 estimated-token recall request budget. Their separate positive product gates remain required.

Require succeeded source operations and phase-one readiness for every history, exactly 200 expected unique question outcomes, and independently validated rubric arithmetic, empty-context/null-score counts, per-category quality, exact answer-visible contexts and tokens, indexing time, generation-only indexing tokens, recall latency and failures. Exclude embedding tokens from generation-performance comparisons and disclose valid partial extraction, missing usage and failed attempts. Inspect incorrect or disputed final contexts and representative correct cases. Failed operations, terminal model failures, degraded retrieval, prefixes and one-conversation diagnostics cannot satisfy full completion. A complete report does not establish a numerical quality/efficiency pass without an explicitly agreed target or prove normal performance.

## 7. Evidence Rules

LLM probes expecting visible content allow at least 1,024 output tokens and reject length termination, empty/malformed content, and reasoning-only output. Embeddings must be finite and dimensionally consistent. Browser/static presence, health, nonempty output, schema compatibility, and passing legacy tests prove only their named boundaries.

Default tests use deterministic fakes and isolated ephemeral databases. Paid endpoints, sensitive data, destructive fault injection, external deployment, repository visibility changes, and image publication require explicit authority and verified targets.

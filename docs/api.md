# Open Agent Memory HTTP API

## Overview

HTTP/OpenAPI is the only required v0.0.1 integration surface. The implemented authentication modes are `dev`, `api_key` and `trusted`; OIDC and LDAP are not available. In `api_key` mode, a user key binds the tenant and `user_id`, and an administrator key cannot select personal content. Retain accepts interactions, the Resource collection accepts documents and the Profile Data collection accepts structured user information, and recall returns cited context without generating an answer. No independent collection selector, browser-only policy or Python SDK is required. The core routes below have PostgreSQL-backed functional coverage; complete-release readiness remains separate work.

## 1. Global Routes

Global routes expose service status and configuration without returning retained user content.

- `GET /health/live` reports process liveness only.
- `GET /health/ready` returns `503` with `ready: false` and `reason: core_only` while later release capabilities are incomplete; it also lists unbound required model roles and never performs model calls.
- `GET /v1/capabilities` publishes contract/configuration/current indexing-recipe identity, implemented features and effective limits. Feature presence is not a model/database availability probe or a release-readiness claim.
- `GET /ui/` serves the same-origin Inspector client with no embedded content or persisted credential.

## 2. Administration

Mode selection belongs to `auth.mode` in the operator configuration. When it is omitted, an active root key selects `api_key`; a fresh rootless database selects loopback-only `dev` and records that selection for restarts. An incomplete root-key bootstrap or an existing keyed database without an active root fails startup. `trusted` must be selected explicitly. `dev` has no authentication or personal privacy boundary and disables key-administration routes. In `trusted` mode, a local data request supplies `X-OAM-Tenant` and `X-OAM-User` without a key; a nonlocal data request also supplies a root key as `Authorization: Bearer <root-key>`. The asserted user must match a path or body `user_id`, and an unknown or disabled tenant cannot be created by assertion. The nonlocal gateway must authenticate callers, replace client-supplied identity headers and block direct access to the data listener. `X-OAM-Role` accepts `user` or `admin` only when the request also carries a valid root key; it cannot assert `root` or bypass the root-key requirement on admin routes.

`POST /v1/users` accepts `{"user_id":"lin"}` from a tenant administrator and atomically creates the personal collection, bound user principal, grant and first user credential. It returns `user_id`, `credential_id` and the secret once after commit. The administrator gets no personal-content grant; old administrator grants remain stored but cannot authorize content under the current SQL function. The user's key governs retain, recall and operation inspection for that user only.

Credential administration issues additional opaque credentials, lists credential metadata, and revokes credentials. Issuance returns each secret once; stored records contain only the SHA-256 digest and immutable tenant/principal binding.

Direct root-key denial is not secrecy from the root operator: an operator who issues and receives a user key can authenticate with that user key.

The implemented credential routes are `GET /v1/credentials`, `POST /v1/credentials`, and `DELETE /v1/credentials/{credential_id}`. Issuance accepts exactly one of a same-tenant `principal_id` or `user_id`, plus optional timezone-aware `expires_at`; `user_id` issues a sibling key for that existing user. It returns the new secret only after commit. Listing accepts `after` and a positive `limit` up to the configured `auth.credential_page_size`, returning metadata and `next_after`. Revocation is idempotent, returns `revocation_effective_by`, and evicts the local cache after commit; unknown and foreign credential IDs have the same response. Every administration request verifies the current credential directly in PostgreSQL.

## 3. Retain and Recall

`api_key` content requests use `Authorization: Bearer <user-key>`; `trusted` uses asserted tenant/user headers and adds a root key on nonlocal binds; `dev` needs no key on loopback. Retain requires an `Idempotency-Key` identifying the logical request; retry with the same key and unchanged input to reuse its receipt instead of duplicating an interaction or append.

Newly asserted personal users in `dev` and `trusted` receive the same Resource, source-control, debug and export grants as newly created keyed personal users. Migration 0012 grants those capabilities to newly asserted users; migration 0013 upgrades existing asserted users only when their grants exactly match the former default, preserving keyed and customized grants. Migration 0014 restricts the registration function's owner and execution permissions. An operator may add missing capabilities for a verified existing user after reviewing that user's intended access.

Write routes resolve the mode-specific identity before consuming the request body. `api.max_request_bytes` bounds the complete encoded body, including JSON escaping or multipart headers/metadata, separately from the interaction-content and Resource-original limits. Its canonical default is 128 MiB and its effective value is published by capabilities. OAM counts actual incoming bytes even without `Content-Length`; an oversized body returns `413 RequestTooLarge` before further buffering/parsing, and partial multipart files are closed. The identity's user binding, grant and semantic content limits are checked after the bounded body identifies its user and input type, before accepting work or making model calls.

| Route | Contract |
|---|---|
| `POST /v1/retain` | Accept a JSON interaction and return `202` with a durable operation and server-assigned source identity. |
| `POST /v1/users/{user_id}/resources` | Accept a text document, HTTPS URL or multipart original; require `Idempotency-Key` and return a durable `202` source receipt. |
| `POST /v1/users/{user_id}/profile-data` | Accept registered structured user information with `profile_data_id`, `subtype` and `content`; require `Idempotency-Key` and return `202`. |
| `POST /v1/recall` | Accept `user_id` and `query`; run non-generative `fast` or `normal` recall, defaulting to `normal`. |
| `GET /v1/users/{user_id}/profile` | Read one stored User Profile content document, references, publication time and processing metadata without generation. |
| `POST /v1/users/{user_id}/profile/refresh` | Return `200` with unchanged stored content and zero generation calls, or `202` with a durable refresh operation; accepts optional `instruction` or `reset_instruction`. |
| `POST /v1/users/{user_id}/search-many` | Accept a caller-provided `queries` list; run one selected recall level with a shared deadline and one divided mode context total, returning ordered per-query outcomes. |
| `POST /v1/users/{user_id}/decompose-and-search` | Accept one query; use one configured planner call to propose bounded searches, or disclose a direct-query fallback, then run the same batch path. |
| `GET /v1/users/{user_id}/resources` and `/resources/{resource_id}` | List or inspect only document Resources, their current versions, passages, abstract state and operation state. |
| `GET /v1/users/{user_id}/profile-data` and `/profile-data/{profile_data_id}` | List or inspect only structured Profile Data, current versions and exact mapped fields. |
| `GET /v1/users/{user_id}/resources/{resource_id}/original` and `/profile-data/{profile_data_id}/original` | Download the retained active original in the matching collection; source HTML is never rendered as an API page. |
| `GET /v1/users/{user_id}/evidence/{source_id}` | Inspect an active chat source's retained interaction envelope and cited L0 passages under the current user policy. |
| `PUT /v1/users/{user_id}/resources/{resource_id}` and `/profile-data/{profile_data_id}` | Create an immutable revision in the matching collection with `Idempotency-Key` and positive integer `If-Match`; return `202`. |
| `DELETE /v1/users/{user_id}/memories/{memory_id}` and `/insights/{insight_id}` | Remove one typed exact learned record; require `source:delete`, commit exclusion and return `202` with the original durable receipt on repeats. |
| `DELETE /v1/users/{user_id}/resources/{resource_id}`, `/profile-data/{profile_data_id}` and `/evidence/{source_id}` | Exclude all versions of the selected source immediately; return a durable cleanup receipt. Wrong-collection IDs return `404`. |
| `GET /v1/users/{user_id}/memories` | List current L1/L2 records, optionally filter by `memory_type=basic` or `memory_type=insight`, and paginate with `limit`/`offset` or `after`. |
| `GET /v1/users/{user_id}/memories/{memory_id}` | Read one eligible L1 record or current L2 Insight revision; require `memory_type=basic` or `memory_type=insight`. |
| `GET /v1/users/{user_id}/operations/{operation_id}` | Inspect accepted work, readiness, failures and usage under the same user grant. |
| `POST /v1/users/{user_id}/operations/{operation_id}/{action}` | Use `cancel`, `retry` or `reconcile-attempt` with the existing operation capability and policy checks. |
| `POST /v1/users/{user_id}/operations/{operation_id}/recover` | Recover failed cleanup/repair for an original removal operation using `source:delete`; preserve its receipt, exclusion and dependencies. |

Operation retry creates a linked receipt for failed/cancelled work and reuses compatible completed checkpoints. Repeat the same retry idempotency key to retrieve that receipt. Selected work with an unresolved external attempt returns `409 RetryRequiresReconciliation`; reconcile the attempt using verified outcome evidence before retrying. Retrying does not require submitting the accepted source again.

### Interaction

The host posts to `/v1/retain` and supplies every message's role, exact content, timezone-aware `event_time` and explicit `learning_eligible` decision. OAM assigns the interaction source identity and uses message order for locators. A saved document-derived assistant answer must remain ineligible for learning.

```json
{
  "user_id": "lin",
  "input_type": "interaction",
  "messages": [
    {"role": "user", "content": "Please keep my checkup summaries concise.", "event_time": "2026-09-23T10:00:00+08:00", "learning_eligible": true},
    {"role": "assistant", "content": "The report lists a September checkup.", "event_time": "2026-09-23T10:00:02+08:00", "learning_eligible": false}
  ]
}
```

Optional `temporal_annotations` use exactly four semantic fields: `role` (`event` or `date_reference`), timezone-aware `start` and `end`, and one unchanged exact `quote`. The quote must occur exactly once in its owning message; use a longer quote to distinguish repeated dates. Equal bounds represent a source-supported point; minute/hour/day or other periods use increasing bounds. Precision, uncertainty and duration wording remain in fact text and quote. The server stores points with `[]` and periods with `[)`, derives origin, and retains the source/request `reference_timezone` as provenance metadata. It accepts no per-annotation instant, granularity, meaning, bounds, origin, reference timezone or character coordinates. Resource annotations additionally name their parsed `locator`, with a quote unique within that block. Returned passage citations identify source/version/message and passage index; fact citations add the canonical passage ID and exact quote. Inspection, export, Insights and Profiles consume the same support identity.

### Text or File Document

A document posts to `/v1/users/lin/resources` with a stable `document_id` within its tenant/user pair and an explicit `update_mode`. Text `replace` supplies the full body; text `append` supplies only the new text for an existing text document. Append concatenates exactly, without inserting whitespace or separators, and allocates the next immutable revision atomically. Include any desired separator in the supplied text.

```json
{
    "input_type": "document",
  "document_id": "checkup-2026",
  "update_mode": "replace",
  "text": "Checkup date: 2026-09-20."
}
```

File documents use `multipart/form-data` on `/v1/users/lin/resources`. The `metadata` part contains `{"input_type":"document","document_id":"scan-2026","update_mode":"replace"}`; the `original` part contains the complete file with its filename and media type. OAM validates size/type and computes its length and digest. File append is rejected; replace the complete HTML/PDF/image file or use a separate document ID.

An HTTPS Evidence URL uses a JSON body such as `{"input_type":"document_url","document_id":"scan-2026","update_mode":"replace","media_type":"application/pdf","url":"https://reports.example.org/scan.pdf"}` on `/v1/users/lin/resources`. The declared media type is one of `text/html`, `application/pdf`, `image/png` or `image/jpeg`. OAM authorizes the user before a single bounded fetch, rejects nonpublic destinations, redirects and mismatched returned bytes, and commits the exact fetched original before indexing. A committed identical idempotency key returns its receipt without another fetch; a failed fetch creates no accepted source. URL ingestion does not crawl links or refresh automatically. A URL query may be needed for fetching but is never included in citations or public error text.

Neither retain format accepts caller-managed `source_id`, `message_id`, `source_version`, `expected_active_version`, `byte_length` or `sha256`. OAM owns source/revision allocation; the latest accepted document revision immediately excludes older derivatives while new indexing is pending. `PUT /resources/{resource_id}` is the compare-and-set revision route: send the same document JSON or multipart shape with matching `user_id` and `document_id`, `update_mode: "replace"`, `Idempotency-Key`, and `If-Match: <active-version>`. It checks the current version before reading an uploaded body or fetching an HTTPS URL and rechecks it atomically at acceptance. An exact retry with the same key reuses its original receipt. Documents remain Evidence and never automatically become learned facts or Insights.

### Recall

The minimal body is `{"user_id":"lin","query":"How should I summarize the checkup?"}`. The host selects `"recall_level":"fast"` explicitly for pre-agent retrieval; later agent calls may select either mode independently. Each mode owns one total for the complete rendered context: `search.fast.context_max_tokens` defaults to 18,000 and `search.normal.context_max_tokens` to 32,768. The total includes learned text, full original bodies, citation quotes, aliases, dates, labels and separators; it excludes the JSON response envelope. There are no caller token-budget overrides or separate fact/chunk budgets.

Full original chunks are included by default. Omitting `include`, sending `"include": {}`, or sending `"include": {"chunks": true}` has the same effect. `"include": {"chunks": false}` omits every full chunk-body item and context block, including Insight source bodies, while retaining eligible facts, Insights, all required supporting facts and citations. Genuine persisted support and alias quotes remain, even when a quote happens to equal a short original. Sources and support are validated under both options. `include: null`, nonboolean `chunks` values and the old chunk-options object are rejected, as are removed recall fields `max_tokens`, `fact_max_tokens` and `max_context_tokens`. Direct, batch and planned search share this contract. Recall never reads or injects the stored Profile. `allow_partial` defaults to false; `include_profile` is rejected. Applications that need personalization separately read `GET /v1/users/{user_id}/profile` and compose inputs under their own model budget.

The returned `context` uses `[n]` to refer to the nth structured item and `S<n>` for distinct source IDs, with source versions shown separately. Full IDs, exact locators, quotes, graph witnesses and time evidence remain in `items`. A fact may reference its selected original passage after exact source/version/message/quote validation; `time=source` appears only when their complete nonempty time evidence matches. Equivalent UTC timestamps may use `Z`. The full-ID format is retained when its rendering is smaller. `context_tokens` reports the complete rendered estimate using the response's `tokenizer` identity, including every emitted quote occurrence and metadata. Exact answer-model token counting remains the caller's responsibility.

Eligible facts, Insights and independent originals compete in final relevance order. An original remains eligible even if extraction produced no facts, unrelated facts or a learned bundle that cannot fit. A learned root is admitted together with its complete required support: supporting facts and citations, plus full original bodies when chunks are enabled. Shared items are returned and counted once. Each tentative complete rendering must fit the mode total; oversized groups are omitted whole while later fitting groups may be considered. The sole exception is a single eligible L1 fact whose complete support bundle exceeds the total: if no higher-ranked root has been admitted, return that complete bundle alone, stop filling and report its overshoot. This exception never applies to Insights; required support and independently selected originals are never clipped. Each mode's `max_results` caps learned items and full original bodies separately; required supporting facts consume learned slots, and false consumes no original-body slots.

Canonical fast uses `lexical_ranking: whole_query`, `partial_match_gate: user_fact_exchange` and `adjacent_user_context: true`; normal uses `per_term`, `"off"` and false. Whole-query lexical retrieval orders one OR full-text expression; per-term ranking retains the existing term-list fusion. Direct dense hits, strict full/primary lexical matches, literal anchors and configured graph results remain independently selectable. Other conversation fact/original roots need a direct dense user fact citing their exact user message or its immediately following assistant reply in the same source revision. Partial assistant-original expansion additionally requires both a dense user fact and its exact cited user original within the first `source_seed_results` raw dense hits. This is a distinct use of the same configured limit; ordinary source discovery retains its fused/diverse seed order. With the gate active, supplemental source discovery is restricted to exact source revisions with an independent user-supported fact hit. The existing global source-seed cap selects query-nearest user originals; they can pass the gate as non-propagating context after their highest-ranked independent user-fact owner and its required support. They retain their later candidate position when the owner is omitted, never create dense/independent witnesses, and cannot authorize assistant replies or recursive discovery. The gate never changes required support or filters Evidence Resources and Insights. If dense retrieval is unavailable under partial recall, diagnostics report the skipped gate and preserve lexical recall. When chunks are enabled, an admitted ordinary fact can additionally retain its already-discovered previous/next user originals; each optional neighbor uses at most `search.<mode>.adjacent_user_context_max_chars` Unicode characters, taking the previous user passage's tail or the next user passage's head. Choose complete sentences first using Unicode sentence-terminal punctuation and the distinct Greek question mark; only if no sentence span fits, use clause punctuation such as commas, semicolons and colons. Decimal separators, compact initials and common abbreviation dots are not sentence ends. Consume attached closing quotes. Discard unproven fragments at existing passage edges; omit the optional neighbor when neither tier yields a nonempty span within the cap. This is conservative punctuation-based segmentation, not a linguistic completeness guarantee. A short neighbor remains complete only when its selected span covers its whole body. Replace the removed `adjacent_user_context_max_tokens` operator key with the character-based key; there is no automatic unit conversion. Sliced items retain their source identity and carry `excerpt: {start, end, original_length}` with zero-based character offsets and an exclusive end; the rendered header marks the same range. An excerpt is optional context, never a new fact citation. Required support remains complete, and a later admitted original, source-owned complete original or support bundle upgrades the excerpt to full text only if that complete representation fits. Source-window fallback alone does not upgrade it. All bodies and excerpt markers share the same context and item caps. A neighbor that cannot fit does not reject the fact. Temporal search continues under these selection rules. Fast makes no model-scoring call.

Both modes also reuse current source-supported entity names and aliases mentioned in the complete query, including names after the ordinary 64-term cutoff. Whole normalized name matching supplies candidate hints without resolving homonyms. Recognized name terms receive space within the existing term cap, and eligible matching facts receive a bounded relevance increase controlled by `search.query_entity_boost`: 0.5 gives a 50% increase by default, and the supported range is 0%–100%. Strict full/primary precedence remains; names alone cannot outrank positive lexical relevance. Per-term mode applies the increase to its existing rank-fusion score as well as its term-list ordering, without another fusion vote. Facts selected through a supported entity hint remain independently eligible through the partial-match gate while keeping their original strict-match status and required citations. Exact identifier/quoted-phrase queries retain their literal path. `diagnostics.local_context.query_entity_boost` and `query_entity_matches` report the effective setting and lexical fact count. Zero skips entity lookup; this recall-only setting requires no reindexing and no generative call.

When a time window has neither directly matched evidence nor qualified temporal seeds, recall can find relevant eligible facts within that window before following temporal links. This recovery preserves the requested time basis and shares the existing candidate, deadline and context limits.

Recall supports only `fast` and default `normal`. Direct, batch and planned requests with `recall_level: "deep"` or `recall_level: "mid"` return `422`; the server does not substitute another mode. Remove obsolete `search.deep`, `search.hierarchy_parents_per_seed`, `search.hierarchy_children_per_parent` and `recall.deep_deadline_seconds` fields from operator configuration before starting this version. Rename `search.mid` to `search.normal`, `search.mid_arm_weights` to `search.normal_arm_weights` and `recall.mid_deadline_seconds` to `recall.normal_deadline_seconds`; obsolete names are rejected. L2 Insight indexing and direct dense/lexical retrieval remain available in both modes; existing indexed content needs no reindexing.

Each mode owns independent `graph: "off" | light | full` and `causal_graph: true | false` settings in [configs/oam.yaml](../configs/oam.yaml). Graph controls entity/alias and semantic expansion: off skips both, light follows stored identities, and full additionally follows semantic neighbors. Causal independently enables bounded outgoing effect-to-cause traversal, including causal edges used by temporal retrieval; disabling it preserves temporal links and date filtering. Fast defaults to graph off and causal false; normal defaults to graph light and causal false. Set both off/false to disable all ordinary graph expansion. Both modes retain direct dense/lexical retrieval, temporal retrieval, and their existing caps, deadlines and context budgets. Quote "off" in YAML. The [configuration model](../src/oam/config.py) rejects invalid graph values and the removed global `search.fast_graph` key. The strict fast-only `fast_graph` request boolean overrides only graph: true selects light, false selects off, and omission/null inherits the mode configuration. It never overrides causal_graph, so fast_graph false can coexist with configured causal traversal. The [direct, batch and planned search handlers](../src/oam/api/search.py) preserve this behavior; true with normal returns 422. Recall diagnostics and correlated logs report both selections, executed arms and degradation. Disabled causal traversal omits its SQL expansion branches rather than merely zeroing their final vote. Entity/semantic and causal results share one graph fusion arm without duplicate votes. Fast always skips reranking. No query wording changes graph selection.

### Profile Data and Refresh

The Profile read response includes `default_prompt`, the current server generation prompt loaded from the packaged [Profile prompt](../src/oam/profiles/prompt.txt). It is available even without a stored Profile or when the API preview budget omits its content. A saved custom `instruction` supplements this base prompt. The Inspector opens the stored Profile directly and uses the server's full preview allowance. Ordinary refresh reuses saved instructions. The optional Customize profile panel contains the instruction editor, an explicit Apply and refresh action, a Use default instructions action when customization is saved, and the read-only expandable default prompt.

`POST /v1/users/lin/profile-data` accepts `{"profile_data_id":"basic","subtype":"basic-profile/v1","content":{"date_of_birth":"1990-05-10","interests":["hiking"]}}` or registered `preferences/v1` content with `example_language` and `domain`. The caller needs the existing `resource:write` grant and `Idempotency-Key`; revision uses `PUT /profile-data/basic` with `If-Match`. Known fields map deterministically to exact User Profile inputs and stay outside ordinary recall. Invalid mappings are rejected before activation. The complete accepted JSON is retained, and a new version supersedes prior exact values. Neither collection accepts a `resource_type` selector. Previously retained originals remain unchanged and readable through the matching collection.

`GET /v1/users/{user_id}/profile` returns one stored `content` string, separate `references`, optional saved `instruction`, `updated_at` from the last publication, and machine-readable `freshness` and processing counts, including `uncovered_inputs` when eligible learned records were not examined or did not fit the bounded model input. `selection_coverage` reports selected, unexamined, and budget-omitted counts for the published revision, or null for an older revision. The Inspector keeps this count in collapsed Generation details. Older field-based stored revisions are rendered into the same document format on read only when every support remains eligible and has a current reference; this performs no generation or database write and preserves the original input identity and publication time. With no readable stored revision, `content` is null. The optional non-negative `max_tokens`, bounded by `profile.max_response_tokens` (18,000 by default), omits the entire document when it exceeds the requested preview budget; it never cuts a claim away from its References. The default text has `## Main content` and `## References`, drawing on selected eligible L1 facts, L2 Insights and exact Profile Data values. L0 source passages validate citations; a fact and its derived Insight are not independent corroboration. L1 changes affect the generation input identity; existing supported stored revisions remain readable until an explicit refresh replaces them. It summarizes current durable context rather than conversation history: resolved corrections appear as the final supported state, temporary test identifiers are omitted, and useful broader activity is summarized briefly. Unknown sex is omitted, a past stated age keeps its source date, and generated prose refers to the individual as “the user.” `POST /v1/users/{user_id}/profile/refresh` accepts an optional bounded `instruction` for custom presentation, including JSON, or `reset_instruction:true` to restore the default. An omitted instruction reuses the saved one. The canonical generation prompt, input budget and instruction participate in refresh identity; a later instruction or reset cancels conflicting active User Profile work before returning the current document or accepting a new operation. Unchanged eligible inputs and instruction return `200` with zero generation calls; changed inputs return `202` promptly and advance pending delayed Insights before User Profile generation when Insight synthesis is enabled. When it is disabled, completed L1 indexing is sufficient and does not wait for Insight coverage. A source still in initial indexing or blocked by its failure returns `409 ProfileInputsNotReady`. Default Markdown citations are positions in the generated support list. Repeated supported IDs are deduplicated with their citation numbers remapped to the same source; unsupported IDs and out-of-range citation numbers are rejected. When a fact or Insight fits only without its source-passage text, the worker can omit that text from the model input while preserving its source identifiers and dates. If no supported evidence or exact fields fit, refresh fails before generation. The worker validates cited support and source eligibility before publication. Reported usage from a completed embedding or a failed generation is retained when the worker still owns the attempt. If a cited source is withdrawn or superseded, the whole old free-form document is withheld until rebuilt. Failed generation preserves the prior revision when its support remains eligible. An ambiguous external model outcome returns `409 ProfileRefreshUnresolved` until reconciled. Evidence-only writes do not change User Profile input identity.

Optional paired `time_basis`/`time_window` override query-date parsing. The half-open window affects temporal ranking only, not other retrieval arms or final inclusion. Without a window, OAM uses one captured UTC reference instant, or the supplied timezone-aware `reference_time` and IANA `reference_timezone`. Supported English/Chinese dates and bounded Japanese expressions can enable temporal spreading even in fast mode. Two absolute calendar endpoints joined by `to`, `between … and`, range punctuation, `到`/`至`, or `から … まで` form a half-open interval including the final calendar day/month/year; local boundaries respect daylight-saving changes. Independent dates, reversed endpoints, immediate `compare`/`compared`/`comparing A to B` syntax, and clock/relative ranges remain ambiguous. Bare `A to B` is supported range notation; the parser does not classify wider natural-language comparison intent. Ambiguous, invalid or unsupported implicit dates leave ordinary recall running with a diagnostic; invalid explicit windows fail validation. Recall accepts no independent tenant or collection selector and makes zero generative model calls.

Batch search uses the same optional mode and time controls for every caller query; without an explicit window, each query is interpreted separately against one frozen request reference instant. The configured `search.max_queries` and per-query query-token limit are checked before any child starts. One mode context total is split into equal shares in input order, with remainders assigned to earlier queries; unused shares are not redistributed. A two-query fast batch therefore receives 9,000 context tokens per child. Each child inherits `include.chunks`, retains its own `items`, complete `context`, diagnostics and estimated rendered count, and applies its share with the same explicit singleton L1 bundle exception. The batch reports `ok` or `partial`, ordered query indexes, summed `context_tokens` and explicit singleton overshoot diagnostics, and safe per-query failure codes; if every query fails, the request is unavailable. A child still running at the deadline is timed out, queued work is canceled, and the read-only child may drain under its own timeout. Capabilities publish the concurrency cap and shared deadline.

Delegated search requires an optional configured planner model role. It keeps the complete original query first and requests complementary evidence queries, rather than paraphrases, with at least 1,024 output tokens. The original and distinct expansions share `search.max_queries`; a single-query capacity searches only the original and reports planner status `skipped` with zero model calls. One reference instant and any explicit or unambiguously inferred original temporal window apply to all children; ambiguous original dates do not create a shared window. The response reports the executed plan, actual planner call count, model-reported usage and any fallback reason. Planner `cost` is null because this release has no authoritative price binding; missing provider usage remains unknown. An invalid or failed planner call uses the original query under the remaining deadline; it never retries the planner. Planning and all child searches share `request.delegated_deadline_seconds`, while every child also retains its selected recall-level deadline. Batch search similarly uses `request.batch_deadline_seconds` for orchestration. A shorter caller deadline remains authoritative. An unfinished planner request may drain after the deadline response, but no child recall starts after expiration. An unconfigured planner is advertised as disabled and the delegated route returns capability unavailable. The planner does not answer the query; each search result still comes from non-generative recall.

## 4. Source Control, Debugging, and Export

### Read All Memory Layers

Read L1 and L2 without a search query through `GET /v1/users/{user_id}/memories`; read L3 through the existing `GET /v1/users/{user_id}/profile`. All require `memory:read` under the authenticated user's tenant and user boundary, make zero model calls, and return only currently eligible content. Resources and Profile Data are separate collections. L3 is one stored Profile document rather than another list of learned records; a missing, unsupported or budget-omitted Profile has `content: null`. Check `freshness` and `omitted` before interpreting an empty Profile; reading never refreshes it.

L3 generation supports a saved custom `instruction` of up to 4,000 characters through `POST /v1/users/{user_id}/profile/refresh`, for example `{"instruction":"Return a JSON profile emphasizing ongoing projects and communication preferences."}`. This supplements the built-in system prompt rather than replacing it; there is no `system_prompt` request field. Refresh requires both `memory:append` and `memory:read` and can generate a new Profile asynchronously. `GET /profile` returns the stored Profile's `instruction` and the current built-in `default_prompt` alongside its content. Refresh with `{}` reuses the stored instruction; `{"reset_instruction":true}` restores default instructions. Do not send `instruction` and `reset_instruction:true` together.

| List parameter | Contract |
|---|---|
| `memory_type` | Optional `basic` for L1 facts, preferences and experiences or `insight` for L2 Insights; omitted returns both. |
| `limit` | Records per page, default `50`, range `1`–`200`. |
| `offset` | Zero-based starting position, range `0`–`9223372036854775807`, default `0`; with `limit=50`, successive pages start at `0`, `50`, `100`. |
| `after` | Optional `unit_id` from `next_after` for cursor pagination; cannot combine with a nonzero `offset`. Keep `memory_type` and `limit` unchanged across pages. |

The response contains `items`, `total`, `limit`, `offset`, `next_offset`, `next_after` and `policy_epoch`. `total` counts all currently eligible records matching `memory_type`, including on an empty or beyond-end page. `next_offset` is null at the end or in cursor mode; cursor mode also returns `offset: null`. Ordering is `created_at DESC, unit_id DESC`, including a deterministic tie-break for equal timestamps. Count and page come from one database statement. Across multiple requests the collection remains live: indexing, removal or revision can change membership and shift offset positions. Use cursor pagination while browsing a changing collection; use export when a fixed captured collection is required. A cursor cannot retain withdrawn content and may become invalid after cleanup.

Each item includes `memory_type` (`basic` for L1, `insight` for L2), `unit_id`, `kind` (`fact` for L1, `insight` for L2), its canonical `memory_id` or `insight_id`, full `text`, `created_at`, `locator`, `citations`, `supports` and `affected_insight_ids`. L2 also includes its current `insight_revision` and descriptive `subtype`; old revisions are excluded. Individual reads use one route, `GET /memories/{memory_id}?memory_type=basic` for L1 or `GET /memories/{insight_id}?memory_type=insight` for L2, and return the same item fields plus `policy_epoch`. The detail path accepts the canonical `memory_id` or `insight_id` selected by the required `memory_type`; do not use the retrieval `unit_id`. Missing or unknown detail types return `422`; the API never guesses the type from an ID. Missing, wrong-kind and ineligible record IDs return `404 MemoryUnavailable`; unauthorized user access returns the existing non-enumerating `404 UserUnavailable`. Invalid pagination or memory-type values return `422`.

List and item reads emit one completion log correlated with the response's `X-Request-ID`, including memory type, pagination metadata, returned counts, outcome and duration. Logs omit credentials and memory text.

Typed detail reads also return `entities`, `relationships`, and `relationships_truncated`. Entities contain a source-supported `entity_id`, canonical `name`, and observed `mention`; an Insight lists entities from its supporting memories. Relationships describe stored `caused_by`, `updates`, `semantic`, `temporal`, and `shared_entity` links to currently eligible learned records, with canonical IDs and readable `text`. For directed links, `direction: outgoing` means the selected memory is the stored source; `incoming` means it is the target. Temporal links are undirected and include `time_basis`, `gap_seconds`, and a `time` object with recorded `memory_start`, `memory_end`, `related_start`, and `related_end` when available. Endpoint ID ordering never implies chronology. Entity co-mentions and shared identity do not assert a typed entity relationship. Detail responses include at most 50 links, prioritizing causal, update, temporal, shared-entity, then semantic links; `relationships_truncated` reports omitted links. Source policy and entity-name witness eligibility apply to both ends.

In `api_key` mode, set `OAM_BASE_URL` to the service origin, `OAM_USER_ID` to the authorized user and inject `OAM_USER_KEY` securely. These are read-only requests:

```bash
curl --fail-with-body --silent --show-error --connect-timeout 5 --max-time 30 \
  "${OAM_BASE_URL}/v1/users/${OAM_USER_ID}/memories?memory_type=basic&limit=50&offset=0" \
  -H "Authorization: Bearer ${OAM_USER_KEY}"
```

Follow `next_offset` until null to consume all L1 pages. For L2 use the same request with `memory_type=insight`. Read one item using its returned ID, and retrieve L3 separately:

```text
GET /v1/users/{user_id}/memories/{memory_id}?memory_type=basic
GET /v1/users/{user_id}/memories/{insight_id}?memory_type=insight
GET /v1/users/{user_id}/profile
```

### Control Sources and Inspect Processing

Selected-unit removal uses the canonical `memory_id` or `insight_id`, which inspection and recall expose separately from retrieval `unit_id` and Insight revision. The route fixes the target kind. Unknown, foreign and wrong-kind IDs return `404 MemoryUnavailable`; missing mutation authority uses the existing unavailable response. Removal makes zero model calls and returns `target_kind`, its typed ID, `operation_id`, committed `policy_epoch`, `cleanup_status` and `reused`. Repeating the same typed ID returns the original operation with current cleanup status. There is no undo. Generic operation cancellation/retry cannot reverse or duplicate the committed removal.

L1 removal excludes the selected Memory Unit and affected Insights immediately, closes the stored Profile until explicit refresh, and preserves sources, passages and unrelated learned records. Cleanup removes owned projection/index/link copies and stale Insight revisions before dependent consolidation can run. Consolidation regenerates the affected Insight under its same ID and next revision when eligible support is sufficient, or records a valid deletion outcome; malformed/refused model output remains a failure. Direct L2 removal cleans all revisions while preserving its supporting facts and never schedules work solely to recreate it. The cleanup receipt lists linked consolidation operation IDs in `stage_state`, so cleanup success and repair outcome are inspected separately. Owned semantic embeddings and lexical index entries are stored on `search_units` and disappear when cleanup deletes those rows; embeddings for preserved sources and unrelated records remain. SQL deletion does not promise immediate forensic erasure of disk bytes. Backups and downloaded exports remain governed by their existing retention/ownership.

Removal maintenance recovery is independent of repeating DELETE. `POST /v1/users/{user_id}/operations/{original_removal_operation_id}/recover` returns `200` with the existing operation response and rearms only `failed_terminal` cleanup or its recorded linked repairs in place. It preserves operation/work IDs, the committed policy epoch, exclusion, support inputs, cleanup dependencies, completed repair outcomes, compatible checkpoints and historical attempts. Succeeded cleanup never reruns; queued/running work and its remaining budget are unchanged. Selected failed work receives the configured attempt budget, a new fence and cleared owner/lease. Admission uses the existing whole-group pending-root count and returns `429` without mutations if newly activated roots exceed capacity. Unknown/foreign operation IDs return `404 OperationNotFound`; non-removal, cancelled, stale-source, or unresolved external-outcome recovery returns `409 RemovalRecoveryConflict`. An unknown outcome first needs the existing ownership-bound `reconcile-attempt` action; recovery never fabricates provider results. This endpoint does not resume cancelled work or settle expired work still marked running, restore removed content, rerun extraction, refresh Profiles or erase backups.

Lifecycle, debug and export use the credential-derived user boundary. Default personal user keys receive distinct `resource:write`, `source:delete`, `debug:read` and `export:read` grants; a root key cannot use these personal routes directly. `GET /resources`, `GET /profile-data`, `GET /memories` and Resource detail/original reads apply current source eligibility and reject a policy change during response assembly. List responses contain current items, a stable-ID `next_after` for the next live page and `policy_epoch`; Insight items also include a descriptive `subtype` (`preferences`, `patterns`, `projects`, `relationships`, `experiences` or `general_insights`), while fact items have `subtype: null`. A cursor does not preserve access to withdrawn content.

Source deletion returns `202` with `source_id`, `excluded_versions`, the committed `policy_epoch`, `cleanup_operation_id` and `cleanup_status`. Exclusion is immediate across recall and inspection; the worker later removes source derivatives and original bytes. Repeat deletion returns the existing cleanup receipt. Revision or deletion makes an in-flight recall unavailable if its source policy changed before result publication, while a new request can still retrieve unrelated active sources.

Each successful direct recall returns `trace_id`. `GET /v1/users/{user_id}/debug/traces/{trace_id}` exposes the bounded recorded candidate arms, query hash/options, final IDs, diagnostics and exact result when every referenced unit, graph-path intermediate node and recorded alias witness remains eligible. `POST /v1/users/{user_id}/replays` accepts `{"trace_id":"trace_...","mode":"inspect_recorded"}` or `"reassemble_recorded"`; these modes make no new model calls and report exact, divergent, expired or policy-redacted outcomes. `GET /v1/users/{user_id}/debug/diff?before=trace_a&after=trace_b` compares currently eligible recorded result IDs and context. A source change that invalidates a candidate or its selected alias support returns `policy_redacted` without old content. Model reruns and User Profile snapshot diff wait for their separate capabilities.

`POST /v1/users/{user_id}/exports` captures the current source set and returns `202` with a ready `export_id` and operation receipt. `GET /exports/{export_id}` returns the format-1 manifest: source revision, policy/generation and projection-epoch identity, per-kind counts, partial-coverage state, SHA-256 checksums and safe relative member paths. `GET /exports/{export_id}/records/{index}` downloads one bounded JSONL part; `GET /exports/{export_id}/originals/{index}` downloads an authorized original. Record kinds distinguish source, L0 evidence and passages, L1 memory/support, eligible entity identities/names/name support/fact memberships, L2 Insight/support, Resource abstracts and the currently eligible L3 User Profile view with its revision and freshness. Download every declared member into its manifest path beside `manifest.json`, then run `oam validate-export <directory>` to verify format, counts, paths, sizes, checksums, source/original identity and L1–L3 support relationships without a server. Source admission, indexing publication, revision or deletion after capture returns `409 ExportPolicyChanged` on later server downloads until cleanup removes the held export; create a fresh export. Already downloaded files remain under caller control.

The bundled `/ui/` Inspector uses these public routes for L1/L2 provenance, the read-only User Profile document and custom refresh instruction, Resource originals and controls, operation readiness and direct recall traces. It holds a user credential only in page memory, renders source and generated text without interpreting HTML, and uses same-origin assets and CSP.

The Insights view uses the typed memory list and opens supporting memories through fresh detail reads. Memory details show entity chips and filterable causal, temporal, shared-entity, update and similarity connections. A focused connection map shows the selected memory and up to six neighboring memories per page; directed links use arrows, and nodes open fresh typed details. A List view retains precise relationship and time details. Original source messages appear in a separate column that stacks below the memory on narrow screens. The Retrieve view submits the original query to `/v1/recall` with the selected `fast` or `normal` mode and `allow_partial: true`, shows coverage, elapsed time, context tokens and returned evidence, and lets users inspect memory results. It returns evidence rather than generating an answer. Failed retrieval requests clear previous results and display an error in the details panel; a request failure is distinct from an empty successful result.

## 5. Response Semantics

Every response carries a request ID and contract version. Accepted asynchronous work distinguishes `accepted`, `source_searchable`, `memory_ready`, `insights_ready`, and User Profile freshness; success at one stage never implies later stages completed.

Recall returns typed `items`, the complete rendered `context`, an estimated integer `context_tokens`, the runtime estimator's `tokenizer` identity, `trace_id`, and diagnostics for query-time interpretation, executed/omitted stages, executed fusion arms, partial coverage, usage and timings. Each Insight retains its subtype and complete admitted support group; empty results do not invent evidence. Selected facts retain citations, time evidence and graph paths. Full original passages preserve their stored text and boundaries and are omitted under `include.chunks: false`. In `context`, facts with verified support in a selected passage are displayed with that passage at the earliest member rank, with the original before derived fact blocks. Other chat citations display source revision, speaker, message ID and exact quoted words; unfamiliar citation shapes retain their complete JSON. A fact inherits source time only when their complete nonempty time evidence matches. Recorded reassembly uses the same deterministic formatting. The complete rendered estimate includes every selected block, citation, qualifier and separator and must fit the applicable mode total or batch-child share except for the reported singleton L1 complete-bundle fallback described above. It is not provider usage; hosts count final model input with their model's tokenizer.

Errors use safe details; authorization completes before external fetches or model calls. Invalid credentials return `401`; write-body overflow returns `413`; a stale `If-Match`, changed idempotent request unresolved User Profile refresh or expired export policy returns `409`; invalid explicit input or URL content returns `422`; an unavailable URL source returns `502`; unavailable capability, mandatory recall stage or in-flight inspection policy returns `503`; exhausted recall deadlines return `504`. Unavailable authority and hidden source/trace/export IDs use a non-enumerating `404` where required.

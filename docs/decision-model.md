# OAM decision model

## Overview

OAM supports an optional model that returns a bounded judgment, such as whether new evidence requires a Profile edit. The design choice is to run ordinary generation directly or to ask Jev first and generate only when needed. Jev made decisions faster than the compact DeepSeek prompt used as an evaluation control. Across the tested cases, Jev plus the generation calls that were still needed took longer than ordinary generation alone. Keep the client opt-in and defer active L2 and Profile shortcuts.

This document covers the decision-model implementation on the v0.2.1 code line and the proposed consumers. A **shadow test** runs the decision on saved inputs and compares it with ordinary generation. The generator remains responsible for any published result.

## 1. Implemented client

The shared client is off in canonical YAML. Enable it with `models.decision.enabled: true` and a nonblank `DECISION_MODEL`. Its configured `DECISION_BASE_URL` and `DECISION_API_KEY` select the decision endpoint independently of the generative model. API and worker deployments can receive the same settings. [Configuration and preflight](operations.md#optional-decision-model)

The Jev-compatible System One request carries text state and named questions. A choice returns a named label, a `noul` returns a yes/no probability, and a score selects a position on an ordered scale. OAM validates answer IDs, types, labels, score bounds and completeness. CLI preflight tests known judgments. Runtime reuses model deadlines and capacity admission and retains provider-reported usage when available. [Request and response types](../src/oam/models/decision.py) · [Runtime client](../src/oam/models/runtime.py)

Current Insight consolidation and Profile refresh use their existing generators. The internal adapter returns judgments to its caller. OAM's workers own memory writes and source-budget admission. [L2 batch worker](../src/oam/indexing/batch.py) · [Profile worker](../src/oam/profiles/worker.py)

## 2. Candidate consumers

**L2 Insight consolidation.** An Insight synthesizes source-backed facts. A proposed shortcut could attach new evidence to an existing Insight if every fact supports the existing wording and the complete group requires no new synthesis. A missing target, contradictory judgment, new claim or uncertain choice sends the whole group to the ordinary generator. A positive decision would still need OAM's evidence, revision and publication checks.

L2 can batch facts from several sources. Any active shortcut must charge its decision to the same source owners as generation and leave enough allowance to generate when needed. Saved inputs, completed stages, and published revisions remain governed by the current batch identity and worker ownership. [Source budget](../src/oam/indexing/budget.py) · [Consolidation and publication](../src/oam/indexing/consolidation.py)

**Incremental Profile refresh.** The current worker first determines whether an existing Profile can be edited incrementally. A compatible snapshot with unchanged inputs already has a zero-call path. The proposed decision would inspect a compatible baseline and the selected changed evidence to see whether wording must change. Full generation, incompatible or custom baselines, and exact Profile Data follow their existing paths. Explicit and scheduled refreshes can reach the same incremental worker. A no-change decision would have to preserve supported claims and account for only the evidence actually examined. [Profile refresh behavior](profiles.md) · [Delta editing](../src/oam/profiles/delta.py)

## 3. Evaluation

The two paths under consideration are ordinary DeepSeek Flash generation and a Jev 1.13.0 check followed by generation when needed. A compact DeepSeek Flash prompt serves as an evaluation control to test whether a short decision prompt provides the same benefit. Each decision path includes the ordinary generation call whenever the decision cannot safely skip it. Times sum serial provider round trips. Tokens are provider-reported, with provider-specific tokenization. Dollar savings are unknown.

| Matched sample | Ordinary generation | Jev + generation when needed | Compact DeepSeek control + generation when needed |
| --- | ---: | ---: | ---: |
| LongMemEval L2, four groups | 25.81 s / 11,438 tokens | 29.67 s / 18,155 tokens | 46.85 s / 20,048 tokens |
| LongMemEval Profile, one incremental refresh | 14.67 s / 18,700 tokens | 15.93 s / 36,945 tokens | 17.37 s / 34,807 tokens |
| Personal Profile blocks, two real inputs and two derived controls | 6.62 s / 4,538 tokens | 7.56 s / 4,579 tokens | 9.22 s / 4,146 tokens |

**LongMemEval.** The isolated OAM run indexed the three original answer-bearing sessions for question `60472f9c` from a 45-session history, published five current Insights, and produced readable full and incremental Profiles. Fast recall used 6,146 context tokens and the judged answer matched the gold count of two. The comparison included four L2 groups with existing targets and the incremental Profile request. All five needed generation. For one L2 group, Jev selected support-only at group level while both seed-level decisions called for generation. The proposed whole-group check would send that group to generation. This source-selected test measures the candidate paths on one question. [LongMemEval benchmark context](benchmarks.md#1-longmemeval-s-at-8k-and-18k)

**Personal Profiles.** A read-only extract from two live OAM accounts yielded two real fact-and-Profile-block pairs. One came from an older Profile because the service used full refresh for that account. The other came from an incremental refresh that preserved its Profile text. Removing the matching block produced two controls that required an edit. All three arms agreed with all four labels. On the two redundant inputs alone, Jev took 1.27 s and 1,077 tokens versus 1.91 s and 2,039 tokens for ordinary generation. The compact prompt took 2.69 s and 929 tokens. The local tests exercised the adapter in a separate process on service-derived inputs. The sample measures individual blocks and deliberate controls. Actual whole-Profile skip frequency, active publication and workload-level savings remain unverified.

**Decision.** Keep optional client support. The strongest measured use was a fast no-change decision on a small, redundant Profile block. Across the personal pilot, the cases that still needed generation erased Jev's latency savings, and the LongMemEval sample had zero safe skips. To break even, the generation saved by safe skips must exceed the cost of all decision calls. Before wiring an active consumer, measure this on representative inputs, count decision failures and all generation calls, and verify that the final published Insight or Profile preserves every required claim.

## 4. Related systems

The public upstream code reviewed on 2026-11-24 shows several ways to use model judgments. A dedicated decision endpoint returns typed answers. A generative call can also yield a structured result by prompting for JSON, and a reranker can return relevance scores through its own interface. The pinned sources establish implementation and defaults. Deployment settings and performance depend on the selected workload and provider.

| OpenViking | Optional Jev/System One reranking scores candidate relevance with independent `noul` questions or a choice request. Reranker failure returns control to the ordinary ranking path. A separate optional Jev matcher checks Scenario relevance and Rule applicability or exceptions. Unavailable judgments preserve candidates. Query planning and memory extraction use generative models. Hindsight's consolidation triage is the closest comparison to the proposed OAM L2 shortcut. TencentDB's Persona gate shows a narrower Profile-related role with different trigger semantics. Mem0 and MemOS provide reference points for keeping the generation or ranking path when an extra decision call offers little savings.
